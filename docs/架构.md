# 抓取管线架构

对应方案 §3–§5（信息雷达、候选抽取、硬排除）与 §3.3（来源注册表）。
方案 §6 的兴趣评分、§7 的探索队列尚未实现；§10 的编辑后台做成了**诊断台**
而不是审批队列，理由见 `决策记录/0002-闸门要自动化.md`。

## 一次运行的完整路径

```
npm run update-events
└─ scripts/update-events.mjs                 只有三行：接线，不含逻辑
   ├─ scripts/sources/index.mjs              SOURCES 数组：19 个来源的注册
   └─ scripts/lib/run-ingestion.mjs          runIngestion(sources)
      ├─ 对每个来源并发 fetchSourcePages()
      │  ├─ assertRobotsAllowed()            先取 origin 的 robots.txt，按 RFC 9309：
      │  │                                   404 → 正常放行；其余 4xx → 放行但标记 robotsUnavailable
      │  │                                   429/5xx → 抛错拒抓；明确 Disallow → 抛错
      │  └─ readPage()                       按 source.accessMethod 分派：
      │       ├─ 'html' → source.parse(html, source)
      │       ├─ 'csv'  → lib/csv.mjs 嗅编码+正规解析 → source.map(record, source, i)
      │       └─ 'json' → source.select?.(payload) → source.map(item, source, i)
      │
      ├─ Promise.allSettled：单个来源失败不影响其他来源
      │  全部失败才抛 AggregateError
      │
      ├─ isPubliclyAccessible()              Big Sight 专用：audience 不含「一般」的直接进待审
      ├─ lib/activity-filter.mjs
      │  └─ filterAndDedupeActivities()      硬排除 → 分流 → 去重
      ├─ lib/pool-db.mjs
      │  └─ upsertCandidate()                写进 candidates 表（不碰 decisions）
      ├─ lib/source-health.mjs
      │  └─ updateRegistry()                 把本轮结果折进 data/source-registry.json
      └─ 写 pool.db + 两份 JSON，把告警打到 stderr

npm run apply-gate    lib/gate.mjs 对 pending 应用规则 → decisions
npm run review        本地后台，人工判决      → decisions
npm run export-site   池子 → events.json（只含 published）+ backstage.json

npm run push-cloud    scripts/push-cloud.mjs：池子里的事实合格集合（无 rejected 判决）
                      + score + tags 单向上行 Turso 镜像；硬排除的连带删除。
                      votes/rounds 只在云端，永不回流本地。
  → Turso（云端）
     ├─ app/api/queue|vote|wantlist   队列 API 三条路由（Bearer QUEUE_TOKEN 保护）
     │    └─ lib/queue.mjs            出题引擎纯函数（本地已有，云端复用）
     └─ app/queue + app/wantlist      前台两页
详见 docs/探索队列设计.md。
```

## 模块边界

**理由码覆盖全部候选，不只是 review/excluded 的。**
2026-08-28 接 CoRich 时发现：`codesFor`（把理由码写进候选池那一步）此前只从
`review` 和 `excluded` 两个桶里取，`keep` 决策的候选从来没把自己的 `signals`
写进池子——因为 `filterAndDedupeActivities` 返回的 `activities` 是裸的事件
对象，不带分类结果。CoRich 386 条候选里 380 条一度落进"理由码为空"，
不是因为没有信号，是因为信号从来没被记下来。修法是在 `run-ingestion.mjs`
里对**全部** `rawFetched` 重新跑一遍 `classifyActivity()`，不再依赖
`filterAndDedupeActivities` 内部已经算过的结果。这个问题其实影响的是所有
来源，只是 CoRich 之前信号命中率极低（剧场标题很少含 `signal:art` 的关键词）
才把它暴露出来。

**`lib/csv.mjs` — 日本开放数据的 CSV**
两件事不能省，都是踩过才知道的：東京都的 CSV 是 **Shift_JIS**，按 UTF-8 读会静默出乱码
（靠数 U+FFFD 替换字符来判断该换哪个解码）；字段里有**带引号的逗号和换行**，
按行 `split(',')` 会把一个 9 行的文件数成 3091 行。

**`scripts/sources/*.mjs` — 来源适配器**
一个来源一个文件。`html` 来源导出 `parseXxx(html, source)` 自己解析；
`csv`/`json` 来源导出 `map(record, source, index)`，取数、编码嗅探与结构化都由管线做完，
适配器只负责字段映射。两者都返回事件候选。
适配器只做**抽取与归一化**，不做取舍判断——"这个活动该不该发"是 `lib/activity-filter.mjs` 的事。
唯一的例外是各来源自己的"这张卡片根本不是活动"（缺日期、缺标题、已过期），那属于抽取失败。

适配器统一用 `scripts/lib/event-utils.mjs` 的 `createEventCandidate()` 造记录，
以保证 id、配色、vibe 的生成方式一致。

**`scripts/lib/run-ingestion.mjs` — 管线骨架**
robots 校验、并发、失败隔离、合并、截断、写盘、状态汇总。不认识任何具体来源。
`fetchSourcePages` 支持 `source.urls`（多页）或 `source.url`（单页）。

**`lib/activity-filter.mjs` — 判定**
三段：

1. `HARD_EXCLUSION_RULES` —— 就活、招生、纯商谈销售等。命中即 `decision: "exclude"`，
   `reasons` 记的是 `hard:recruiting` 这样的**命名理由码**，不是正则源码。对应方案 §5.1。
2. `PUBLIC_EXPERIENCE_RULES` —— 命中即 `decision: "keep"`，`reasons` 记 `signal:tech`
   这样的码；没命中则 `decision: "review"`，`reasons` 记 `review:no_public_experience_signal`。
   **每条判定都至少有一个理由码**，由测试保证。正向匹配另外单独记在 `signals` 里，
   即使被硬排除压过也保留——自动闸门需要知道"它其实也命中了机器人"这件事。
   `signals` 里还包含 **`PLACE_SHAPE_RULES`** 从 **`place`（地址）** 而非标题读出的码
   （`signal:off_street` 楼上或地下 / `signal:residential_room` 住宅楼一室 /
   `signal:in_building` 在某栋楼里）。**它们从不影响 keep/review 判定**——
   "在楼上"和"有不有趣"无关，那属于 0002 留给人的一半。
   新增或修改规则后，用 `node scripts/backfill-signals.mjs --write`
   给已入池的候选重算码：码是入池时算好存下的，日常来源会在下一轮自愈，
   但手动的 `collect-*` 来源不重跑就会一直停在旧规则上。
3. `dedupeActivities()` —— 按归一化标题与归一化 URL 去重。URL 归一化会去掉 hash、
   utm/fbclid/gclid 等追踪参数、末尾斜杠，并对 query 排序。

> **这一层不再决定发布。** 自 2026-08-28 起，抓取只把候选写进 `data/pool.db`，
> 发布是 `decisions` 表里的一行。理由码从这里来，但「上不上前台」由人或规则另判。
> 见 `决策记录/0003-候选池与后台.md`。

**`lib/source-health.mjs` — 来源健康**
纯函数，不碰 fs、时钟、网络，`now` 由调用方给。它解决的是「解析器悄悄失配」：
来源仍然 200、仍然解析成功，只是一条也匹配不到了——看上去和"今天没活动"一模一样。
判据是拿来源自己的近期历史比：

| 告警码 | 触发 | 级别 |
|---|---|---|
| `fetch_failed` | 本轮抓取失败 | 警告 |
| `fetch_failed_repeatedly` | 连续失败 ≥3 次 | 严重 |
| `empty_parse` | 抓取成功但 0 条，而历史基线 >0 | 基线 ≥3 为严重，否则警告 |
| `count_drop` | 条数低于历史中位数的 50% | 警告 |
| `stale` | 距上次成功超过 `expectedUpdateWindowDays` | 警告 |
| `robots_unavailable` | robots.txt 返回非 404 的 4xx | 警告 |

基线用的是**去掉本轮之后**的成功轮次中位数，否则今天的 0 会把自己的基线拉下来。
`empty_parse` 分两级是因为藝大正木纪念馆这类场馆本来就常年无展，0 条是常态。

**`lib/editorial-labels.mjs` — 人的判断**
纯函数。把人工标注和候选合到一起，算三样东西：标注覆盖率、
**每个理由码与人判断的吻合度**、以及把现有规则当闸门打开的试算。
它不参与管线。详见 `决策记录/0002-闸门要自动化.md`。

**`lib/` 下的其余模块**
`event-contract.mjs` 定义字段契约；`near-duplicate-events.mjs`、`publication-policy.mjs`、
`university-publication-policy.mjs`、`editorial-context.mjs` 各自被 `scripts/` 下的
一次性脚本调用，**目前都不在 `update-events` 主链路上**。
`shop-publication-policy.mjs` 现在只剩一个 `shopWhy()`，由开闭店链路调用——
它原本那半边（自行决定发布的 `DISTINCTIVE` 正则）2026-08-28 删掉了，见下文。

**开闭店是另一条链路**
`npm run collect-shop-changes` → `scripts/collect-shop-changes.mjs`
→ `minkei.mjs` 家族（15 个地域版共用一个解析器）→ `lib/pool-db.mjs`。
它不经过 `run-ingestion.mjs`，因为是两段式抓取（先首页取线索，再只抓命中的文章页），
频率也低得多。对应方案 §3.2 的「店铺生命周期」与「小型文化与亚文化」。

它**曾经绕过候选池直接写 `data/events.json`**，2026-08-28 改成写池子。
那个旧行为既违反「没有任何抓取代码路径能让东西上前台」，产出又会被下一次
`export-site` 从池子重建时抹掉——两个问题一起修掉了。
经过与推广出来的规矩见 `决策记录/0004-采集脚本一律写池子.md`。

**来源家族**：一个解析器配 N 条注册，用 `minkeiSources()` 这样的工厂**摊平**成普通
来源项，而不是在管线里加嵌套结构。健康监测用 `name::url` 做 id，因此某一版改版失效
不会被其他 14 版的正常数据掩盖。

**展会出展者目录是第三条链路，手动触发**
`node scripts/collect-handmade-marche.mjs` / `node scripts/collect-maker-faire-tokyo.mjs`
→ 各自的 `scripts/sources/*.mjs`，直接调 `openPool`/`upsertCandidate` 写入候选池，
不经过 `run-ingestion.mjs` 也不进 `data/source-registry.json` 的健康监测——这类
来源的"正常"状态本来就是长期为空（展前几个月出展者页还没数据），硬套
`empty_parse`/`stale` 告警毫无意义。详见 `docs/来源清单.md`「手动/偶发触发来源」一节。

## 失败处理

- 单来源失败：`console.error` 一行，`sourceStatus[i].ok = false` 并带 `error`，其余来源照常。
- 全部失败：抛 `AggregateError`，退出码非 0，CI 会红。
- 静默失效由 `lib/source-health.mjs` 兜住，见上表。告警打到 stderr，
  并写进 `data/source-registry.json`；`npm run check-sources` 读它，
  有严重告警就退出码非 0。
- CI 里 `check-sources` **排在提交数据之后**：解析器坏掉应该让构建红，
  但不该顺带丢掉那些正常来源当天抓到的内容。

## 候选池与后台

**`lib/pool-db.mjs` — 记录之源**
SQLite（`node:sqlite`，零依赖），两张表：`candidates` 由抓取重写，
`decisions` 只由人或规则写。**没有判决行 = pending**，所以重抓不可能撤销任何决定。
`firstSeenAt` 跨轮保留，是「今天真的新来了什么」的唯一依据。

**`lib/object-type.mjs` — 分门别类**
按方案 §4.1 推出 event / exhibition / place / opening / closing / activity /
open_facility。从来源已有的证据推（changeType、genre 标签、来场对象、日期跨度），
不手填。§7.1 要求探索队列一轮里类型多样，「全都叫活动」保证不了多样性。

**候选的单位是「一趟出行」，不是「一个实体」**——见方案 §4.3。
一栋楼里的 207 家店是**一条**候选，不是 207 条：对"这周末去哪"它们只有一个答案。
已落地的是「一个地址一个候选」，诊断在 `scripts/check-granularity.mjs`。
更模糊的边界（同一片区、同一天的多个点）留到探索队列开工时处理。
新增来源时的自检：**如果两条候选都被放行，用户会因此多出门一次吗？**

**`lib/gate.mjs` — 自动闸门**
规则写和人同一张 `decisions` 表，只是 `decidedBy` 从 `human` 变成 `rule:<名字>`。
加规则的门槛是**证据事实且权威**，不是「过滤器通常对」。三条规则，三类证据：

- `rule:trade_only_admission`——主办方自己填的入场对象（`来場対象者=商談`）
- `rule:not_a_destination`——内容类型本身不是可去处（`hard:submission_call` /
  `hard:bulletin` / `hard:on_sale_announcement`），和「是否有趣」无关，
  来自 2026-08-28 第一轮人工/AI 联合判决拆出的结构性规律，见
  `决策记录/0003-候选池与后台.md` 附录。
- `rule:not_open_to_public`——场馆自己登记的公开区分（産業貿易センター 的
  `招待` / `関係者のみ`）。没有徽章的行保持 pending：「没写」不是一种声明。

反面的例子同样重要：开闭店链路原来那条 `DISTINCTIVE` 正则（初出店/専門店/
ユニーク/コンセプト）**没有**被升级成闸门规则，因为「这家店够不够独特」是
"有不有趣"的判断，属于人的那一半。

**`lib/ranking.mjs` — 排序与标签：规则的第三种用法**
闸门只会「判决」，门槛也刻意定得很高。2026-08-29 跑判据的结果说明了代价：
**样本足够的七个码里，没有一个放行率接近 0 或 1**——
`signal:theater` 63% / `signal:tech` 55% / `signal:in_building` 48% /
`signal:hands_on` 42% / 无信号 35% / `signal:art` 25% / `signal:off_street` 21%。
25% 的码做不了规则（按它排除等于每四个好候选扔掉一个），但它是**真实信息**，
而 2,600 条待判按日期平铺把这份信息完全浪费了。

所以这个模块做闸门做不了的事：**排序与打标签，不做任何判决。**
它不写 `decisions`，也不可能让任何东西上前台或下架，只改变人先看到什么。

- **权重来自实测放行率**，不是手调的：`weightsFromEvidence()` 读
  `gate-evidence` 的结果，样本不足 10 条的码权重为 0——0002 说过"第一轮判决还不算证据"。
- **三项的量级是刻意分层的**：`closing` +1（截止日是唯一等不了的事）＞
  证据 ±0.5 ＞ 临近度 ≤0.25。**临近度最小**——否则队列就退化成日历了。
- **按来源与会场双重轮转**。两种失败都在真实数据上见过：按日期排，708 个手作
  市集摊位连成一片；只按会场轮转，CoRich 又接管了（它 363 场各在不同剧场，
  于是全部并列第一）。现在一轮里每个来源出一条，实测**前 20 条覆盖 19 个来源**。
- 每行带 `clusterSize`，调用方可以折叠尾巴（"这家展会还有 707 个摊位"）。

**`lib/learning-value.mjs` — 按「判了能学到多少」排队**
`ranking.mjs` 回答"想让站上东西好，人该先看什么"。这个模块回答另一个问题，
而 2026-08-30 它更要紧：**瓶颈是人。** 934 条待判，人一次能判几十条不是几百条，
所以这几十次判断该花在收益最大的地方。

当天实测：池子里有 **75 种不同的码签名，其中 39 种从来没判过、覆盖 337 条待判**；
而最大的那种签名（283 条无正向信号的 `place`）只判过 3 条。
**判第 284 条已知类型学不到东西，判某个没见过的类型的第一条能学到很多。**

一次判断的价值 = **不确定度 × 覆盖面 × 新鲜度**：

- **不确定度**——从没判过 = 1；判过则用 `4p(1-p)`（五五开时最大，一边倒时趋 0），
  且样本很薄时（1–2 条）仍按"基本未知"算，这是 0002「第一轮判决还不算证据」的微缩版。
- **覆盖面**——同签名的待判条数，取 `log2`：**大 14 倍的组不该有 14 倍价值**，
  否则最大的那组会霸占整个队列，人一整轮只学到一件事。
- **新鲜度**——从没判过的组额外加权，第一条判决比第四条值钱。

**这不是质量分。** 一条候选可能正因为"没人知道这类东西好不好"而排在最前面。
同样按签名做轮转，一轮里每种问题只出一条。

**`lib/gate-evidence.mjs` — 给闸门攒判据**
对每个理由码统计「被它命中且已判决的候选里，人实际放行了多少」。
放行率高＝这条规则拦错了；低＝可以依赖。样本不足 10 条标灰。

**两个入口**
- `/backstage`（站上，只读）：同一套设计语言，分类展示整个池子。
  只读是刻意的——公开 URL 不是改状态的地方。
- `npm run review`（本地，可写）：放行 / 排除 / 撤销，底部带判据面板。
  只绑 loopback，直接写 git 里的库。

**判决 ≠ 发布**：`npm run review` 之后要跑 `npm run export-site` 站点才变。
