# 探索队列 v1 设计

2026-08-31 头脑风暴定稿。落实方案 §7 的第一版：单人、部署带后端、闸门降级。
配套决策见 `决策记录/0006-闸门降级与品味分家.md`。

## 1. 概念变化

- **闸门降级为纯事实闸门。** `decisions` 只回答「能不能收录」——硬排除
  （非公众、信息可疑、不是可去处、已消失）。「好不好去」不再是判决问题。
- **品味层是云端 `votes` 表**，由用户在队列里滑出来。votes 永不写回
  `decisions`，`taste_no` ≠ `rejected`（方案 §9 的教训）。
- **「published」语义退役。** 前台不再有「已发布集合」；事实合格
  （= 无 rejected 判决）的候选全部是队列题源。积压的 pending 不再等人判，
  自然消化。
- **从零滑起。** 历史人工 published 不预填「想去」，只作为事实合格证据。

## 2. 数据分家

```
pool.db (本地，记录之源：候选 + 事实判决)
  └─ npm run push-cloud ──单向──▶ Turso (云端)
                                    ├─ candidates  镜像，事实合格集合
                                    └─ votes       品味层记录之源，永不回流
```

- `push-cloud`（新脚本）：把事实合格集合 upsert 到 Turso 的 `candidates`
  镜像表（结构照抄本地），**硬排除的从云库删除**。单向，无回流，无双向同步。
- Turso `votes` 表：`candidateId, vote ('want'|'ok'|'no'), votedAt, roundId`。
  votes 是品味数据的唯一记录之源；pool.db 对它一无所知。
- 抓取/判决链路完全不动：抓取只写 `candidates`，判决只写 `decisions`，
  `upsertCandidate()` 仍是采集唯一写入口（0003/0004 不变）。

## 3. 队列生成（云端 API）

每轮约 15 条。纯函数放 `lib/queue.mjs`，API 层薄壳。

**硬过滤**：未滑过（或 `ok` 冷却期满）、未结束、startDate 在 180 天窗口内、
事实合格。

**配比**（§7.1 的单人冷启动版）：

| 约 | 内容 | 依据 |
|---|---|---|
| 1/3 | 现在性：closing、即将开始 | `changeType` / `startDate` |
| 1/3 | 证据 + popularity 高分 | `lib/ranking.mjs` 的 scoreFor |
| 1/3 | 家族多样性轮转 | 按 source 家族 round-robin |
| +1–2 | 受控探索：从没出过题的类型/家族 | 出题历史 |

**有限队列**：滑完一轮才能开下一轮（Steam 规矩）。轮次记 `roundId`，
出过题未滑完的下轮继续。

## 4. 反哺（v1 规则，不做学习）

| 滑动 | 效果 |
|---|---|
| 想去 want | 进想去清单；不再出题 |
| 可以 ok | 冷却 30 天后可重出 |
| 不想去 no | 不再出题（这是 taste_no，不碰 decisions） |

votes 攒起来，将来像后台判据面板一样从里面长规则；v1 不做任何模型。

## 5. 前台

两页，替换现在的全量铺开页：

- **队列页**：一次一卡——标题、时间地点价格、为什么现在（closing/临期/
  popularity）、来源链接；三个按钮。滑完显示本轮小结。
- **想去清单页**：右滑过的，按日期排，临期高亮。

**不公开**：两页都要 token（env 里一个秘密，cookie 存住，单人够用）。
读写 API 同一 token 保护。

## 6. 测试与运维

- 配比、硬过滤、冷却、轮次推进全部纯函数单测（`lib/queue.test.mjs`），
  不依赖 Turso；Turso 访问层单独薄壳。
- `push-cloud` 幂等，可重跑；失败不影响本地链路。
- 来源健康监测不变；云库只是导出目标之一，地位与 `events.json` 当年相同。

## 7. 明确不做（v1）

- 朋友组、匹配揭晓、异步投票（方案 §8，等第二个用户）；
- 从 votes 学品味模型；
- 行程层/地理聚合（已知问题 6）;
- 手机 App——部署后手机浏览器直接能用即达标。
