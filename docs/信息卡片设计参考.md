# 信息卡片设计参考

**日期：** 2026-08-28
**状态：** 调研，未改代码

要接餐厅、音乐剧、剧本杀这三类新内容之前，先看现有应用把哪些信息摆在明面上——
不是照抄字段，是确认我们的卡片该不该跟着改。方法是直接看真实页面的结构，
不臆测。

## 结论先说

**不需要改 `lib/event-contract.mjs` 的字段结构。** 三个垂类研究下来，
真正区别于现有内容的字段（车站+步行分钟、剧本人数、场次时长）都是"塞进现有
自由文本字段就够"的量，不值得为它们单开列。真正值得记住的是两条更根本的
发现，和我们已经做的东西直接相关：

1. **编辑理由句是第一位的，结构化字段是第二位的。** Time Out Tokyo 的
   列表压根不放价格，每条都是一段"为什么值得去"的短文——这正是我们
   `why` 字段 / `editorial-context.mjs` 已经在做的事，调研确认这条路对。
2. **CoRich 的"想看人数 / 已看人数"双计数**——这不是我们缺的字段，
   是方案 §7.3「三态判断」和卡片里 `mates` 字段**已经打算做但还没实现**
   的东西，在真实产品里已经验证过存在。等探索队列做起来时可以直接参考
   这个双计数的呈现方式。

## 逐个垂类实测

### 餐厅：HotPepper グルメ 首页 + UX 研究综述

页面结构显示的字段：菜系分类（居酒屋/烧肉/意面等）、地区+最近车站、
价格区间（**午餐和晚餐分开标**）、包间/贵宾室、可容纳人数、
吃到饱选项、是否支持在线预约。

跨应用的 UX 研究（Baymard、多篇案例研究）总结出的决策三件套是
**地图 + 大致价格 + 朋友的评价**，图片用来判断"这地方氛围对不对"。
一个反复出现的设计张力是：信息越全越让人信任，但也越拖决策速度——
建议用"默认轻、点开才深"的渐进展开，而不是一次性把所有字段堆上卡片。

**落到我们的字段**：车站+步行时间归进现有的 `place` 字符串（本来就是
自由文本，来源适配器只要养成"有车站信息就带上"的习惯）；午餐/晚餐价格
分开这件事，`price` 字段本来就是自由文本，可以直接写成
`"午餐 ￥1200 起 · 晚餐 ￥4000 起"` 这样的形式，不需要拆两个字段。

### 剧本杀：mdms-mania.com 门店列表

字段：店名、地址、最近车站+步行分钟、电话、营业时间、官网链接、
**剧本标题、玩家人数、场次时长、单场价格**、剧本详情页链接。

剧本杀这类内容天然是 `place`（方案 §4.1 的"值得专程去的场所"），不是
按日期排的 `event`——一家店同时开着好几个不同剧本，每个剧本才有具体的
人数/时长/价格。这和我们现有 `event-contract.mjs` 的一条记录对应一个
"去处"的设计吻合：**每个剧本注册成一条记录**，而不是把一整家店塞进一条。
玩家人数、场次时长这类信息量小，直接写进 `description` 就够，
不需要专门开字段——这类字段目前不参与任何判定逻辑（不像
`来場対象者` 那样会喂进闸门），开专门字段的收益不成立。

### 音乐剧/小剧场：CoRich 舞台芸術！

实测抓到的字段：剧目名、剧团/制作方、剧场名+地区、演出档期（起止日）、
状态标签（上演中/もうすぐ開幕/もうすぐ閉幕）、价格区间、
**「想看人数 + ♪评分」「已看人数 + ★评分」两组独立计数**。

最后这条值得多说一句：CoRich 把"我想看"和"我看过"分成两套完全独立的
计数和评分，而不是混在一起。这正好对上方案 §7.3 写的三态判断
（想去/可以/不想去）和卡片里已经留好但还没接的 `mates` 字段——
说明这个产品形态在真实世界里是验证过的，不是我们凭空设计的。

### 综合参照：Time Out Tokyo（定位最接近我们）

这是几个调研对象里**产品定位离我们最近**的一个——不是搜索引擎，是编辑策展。
实测它的列表**不放价格**，每条给一段解释"为什么现在值得去"的短文
（比如高円寺阿波踊り那条会讲"1957年商店街为振兴街区办起来的活动，今年又办了"），
配图、地区、日期区间作为辅助元数据。

这验证了我们已经在做的方向：`lib/activity-filter.mjs` 之外还有
`lib/editorial-context.mjs` 在给不同来源生成理由句，`why` 字段在卡片上
是主角。**唯一要留意的是：以后接餐厅/剧本杀这类新品类时，也要走
"生成一句为什么值得去"这条路，不能只是把结构化字段堆上去当理由。**

### 背景：discovery queue 设计的学术依据

关于"发现队列"设计的综述研究把有效的意外发现归结为三个可调的杠杆：
**趣味性、多样性、非预期性**。这和方案 §7.1 已经写好的配比表
（30% 兴趣相符 / 20% 朋友强兴趣 / 20% 新开将消失 / 15% 编辑精选 /
10% 相似群组 / 5% 完全新领域）是同一套逻辑——调研没有推翻这张表，
是给它找到了外部依据。

## 对接下来实现三个来源的具体指导

1. **不改 `event-contract.mjs` 的字段列表。**
2. 新适配器（HotPepper、mdms-mania、CoRich）都要在能拿到车站/步行时间时
   写进 `place`，能拿到分场景价格时写进 `price` 的自由文本里。
3. 每个适配器都要生成一句 `why`（哪怕是模板拼接：「剧本杀 · N 人 · 约 N 小时」
   这种也比空着强），不要只填结构化字段就了事——这是 Time Out Tokyo 和
   我们自己 `editorial-context.mjs` 共同验证过的路。
4. 剧本杀按"一个剧本一条记录"接，不按"一家店一条记录"接。
5. CoRich 的双计数模式记下来，等做探索队列的三态反馈（方案 §7.3）时
   有真实产品可以参考实现细节。
