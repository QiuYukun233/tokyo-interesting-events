# 数据契约

**`data/pool.db` 是记录之源，其余 JSON 都是它的导出。** 见
`决策记录/0003-候选池与后台.md`。

事件记录的字段契约在 `lib/event-contract.mjs`，由 `lib/event-contract.test.mjs`
对 `data/events.json` 的真实内容做校验。**改字段要同时改这三处和本文档。**

## `data/pool.db`（SQLite）

两张表，分工是这套设计的核心：

```sql
candidates   -- 抓取找到了什么。每轮 upsert 重写。
decisions    -- 人或规则得出了什么结论。抓取永远不碰。
```

`candidates` 除了事件记录的字段，另有：

| 字段 | 说明 |
|---|---|
| `objectType` | 方案 §4.1 的对象类型，写入时由 `lib/object-type.mjs` 推出 |
| `reasons` / `signals` | 理由码与正向信号，JSON 数组 |
| `popularity` | 来源报告的关注计数（CoRich：観たい+観てきた 之和）。NULL＝来源没有此信号；0＝来源报告为零，两者要分开。约 85% 的公演为 0，所以这是分桶信号（「有十几个人关注」vs「无数据」），不是排序分 |
| `firstSeenAt` | **跨轮保留**，用来区分「今天真的新来了」和「今天又抓了一遍」 |
| `lastSeenAt` | 最近一次被抓到 |

`decisions`：

| 字段 | 说明 |
|---|---|
| `candidateId` | 主键，一条候选至多一个判决 |
| `state` | `published` \| `rejected`（受 CHECK 约束） |
| `decidedBy` | `human` \| `legacy` \| `rule:<名字>` |
| `reason` / `note` / `decidedAt` | 判据、备注、时间 |

**没有 `decisions` 行 = pending。** 这不是一个字段，所以没有任何抓取代码能重置它。

## `data/events.json`（导出）

前台（`app/page.tsx`、`app/pool/page.tsx`）直接 import 这份文件，没有运行时抓取。
由 `npm run export-site` 从池子生成，**只含 `state='published'` 的候选**，
按 180 天窗口过滤、上限 300 条。抓取不会改动它。

```jsonc
{
  "updatedAt": "2026-08-28T00:59:57+09:00",  // 东京时区 ISO
  "updatedAtLabel": "今日 00:59",             // 前台直接显示的中文标签
  "sourceStatus": [ /* 每个来源一条，见下 */ ],
  "events": [ /* 事件记录，见下 */ ]
}
```

### 事件记录

必填（缺任一即校验失败）：

| 字段 | 说明 |
|---|---|
| `id` | `stableEventId(来源名, sourceUrl, 标题)` 的 12 位十六进制。同一活动跨次运行稳定 |
| `startDate` | `YYYY-MM-DD` |
| `title` | 原文标题（多为日文） |
| `titleZh` | 中文标题。目前多数来源直接复制 `title`，尚无翻译环节 |
| `place` | 场地，缺省 `东京都内 · 详见主办方` |
| `time` | 人读的时间描述，缺省 `详见活动页` |
| `price` | 人读的价格描述，缺省 `详见活动页` |
| `vibe` | 编辑标签，由 `vibeFor()` 从文本推出 |
| `sourceUrl` | 回链主办方 |

选填（可以缺席；出现时必须是字符串）：
`endDate`（`YYYY-MM-DD`）、`source`、`imageUrl`、`why`、`changeType`、
`attribution`、`audience`、`description`。

**`ongoing`（布尔，池子里的列，2026-08-28 加）** ——「常驻，无已知结束日」。
不是选填字符串，独立说明：

> **缺 `endDate` 有两种截然不同的含义**，此前无法区分：单日活动，
> 和「一直办到另行通知」（SCRAP 的「開催：2024年12月29日〜」、一家店）。
> 池子的窗口过滤按 `COALESCE(endDate, startDate)` 算，于是把后者当成前者，
> **24 条仍然可订的密室游戏就这样悄悄跌出了后台**，直到 2026-08-28 才发现。
>
> 现在 `ongoing = 1` 的候选不受「已经结束」这一半的过滤，但**仍然受
> 180 天上限约束**——"没有已知结束日"不等于"不管什么时候开始都要显示"。
>
> 只有在**来源自己这么说**的时候才置位：SCRAP 是句尾那个孤零零的 `〜`，
> 店铺是"店本来就没有结束日"。不是猜出来的。

前台展示用但不在契约里：`color`（取自 `COLORS` 四色）、`symbol`（取自 `SYMBOLS`）、
`mates`（想去人数，目前恒为 0，社交功能未实现）、`category`。

### 不变量

- `events` 按 `startDate` 升序。
- 已结束的活动不出现（`endDate || startDate` 早于当前时刻即剔除），
  **除非 `ongoing`**——那是常驻、无已知结束日的东西。
- `startDate` 不超过当前时刻 **180 天**。
- 最多 **80** 条。
- 去重键是 `${sourceUrl}:${title}`；优先级 `manual > fetched > existing`，
  也就是人工数据覆盖抓取数据，抓取数据覆盖上一轮的旧记录。

## `data/review-events.json`

候选诊断队列，由 `npm run review` 消费。装的是**没有直接 keep 的全部候选**：
`review` 判定的、Big Sight 仅限商谈的、以及被硬排除的。

```jsonc
{
  "updatedAt": "...",
  "sourceStatus": [ /* 与 events.json 相同 */ ],
  "events": [
    {
      "activity": { /* 与上面的事件记录同构 */ },
      "decision": "review",
      "reasons": ["review:trade_only_admission"],
      "signals": []
    }
  ]
}
```

- **`reasons` 永不为空**，由 `lib/activity-filter.test.mjs` 保证。取值是命名理由码，
  人读的标签在 `REASON_LABELS` 里：`hard:recruiting`、`hard:admissions`、
  `hard:trade_sales`、`signal:tech`、`signal:hobby`、`signal:art`、`signal:hands_on`、
  `signal:nature`、`review:no_public_experience_signal`、`review:trade_only_admission`。
- **`signals` 单独记正向匹配**，即使该条被硬排除也保留。自动闸门需要知道
  "它其实也命中了机器人"这件事。
- **进了这份文件不代表没发布。** `review` 条目同样在 `events.json` 里——
  发布目前没有闸门，见 `决策记录/0002-闸门要自动化.md`。

## `data/manual-events.json`

编辑精选，格式与 `events.json` 的单条事件一致，人工维护。每轮合并时优先级最高。

## `data/source-registry.json`

来源注册表的**观测部分**（静态部分在 `scripts/sources/index.mjs`）。
由管线每轮改写，`npm run check-sources` 读它。

```jsonc
{
  "updatedAt": "2026-08-27T16:38:21.561Z",
  "entries": [{
    "id": "東京都美術館::https://www.tobikan.jp/exhibition/",  // name 不唯一，藝大三个馆同名
    "name": "東京都美術館",
    "sourceFamily": "museum", "trustTier": "S0", "accessMethod": "html",
    "crawlFrequency": "daily", "expectedUpdateWindowDays": 14,
    "robotsAndTermsCheckedAt": "2026-08-28", "parserVersion": "2026-08-27",
    "robotsUnavailable": false, "ownerOrContact": "东京都美术馆",
    "lastRunAt": "...", "lastSuccessAt": "...", "lastItemCount": 7,
    "lastError": null, "failureStreak": 0,
    "history": [{ "at": "...", "ok": true, "count": 7 }]   // 最近 14 轮
  }],
  "alerts": [{ "id": "...", "name": "早稲田大学", "code": "robots_unavailable",
               "level": "warning", "detail": "…" }]
}
```

`history` 是告警的判据来源，别手改。告警码与级别见 `架构.md`。

## `data/backstage.json`（导出）

`/backstage` 页读这份。整个池子（180 天窗口内），按对象类型分组，
每条带 `state`、`decidedBy`、`reasons`、`signals`、`firstSeenAt`。
另含 `summary`（各状态/类型/来源计数）。

```jsonc
{
  "updatedAt": "...",
  "summary": { "total": 236, "pending": 126, "published": 30, "rejected": 101, "byType": [...], "bySource": [...] },
  "groups": [{ "objectType": "activity", "label": "可参与的体验", "items": [ /* ... */ ] }]
}
```

分组顺序固定为 `lib/object-type.mjs` 里 `OBJECT_TYPES` 的声明顺序。

## `sourceStatus`

```jsonc
{ "name": "Tokyo Big Sight", "ok": true, "count": 10, "pages": 1, "error": "..." }
```

`count` 是**解析出的原始条数**，不是最终发布条数——过滤和去重发生在这之后。
`error` 只在 `ok: false` 时出现。
