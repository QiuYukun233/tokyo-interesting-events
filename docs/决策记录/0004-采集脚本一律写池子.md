# 0004 · 采集脚本一律写池子，不写别的地方

**日期：** 2026-08-28
**状态：** 生效
**补强：** [0003](0003-候选池与后台.md) 定下的「抓取只写 candidates，判决只写 decisions」

## 背景

0003 立了规矩：**没有任何抓取代码路径能让东西上前台。** 主管线
（`run-ingestion.mjs`）确实照办了。但它是作为一句约定写下的，
**没有任何机制去保证它。**

2026-08-28 检查开闭店链路时发现，`scripts/collect-shop-changes.mjs` 从来没有
遵守过这条规矩。它读 `data/events.json`，把自己用一条 `DISTINCTIVE` 关键词正则
（`初出店|専門店|ユニーク|コンセプト|…`）挑中的合并进去，再写回同一个文件。
也就是说，这个脚本自己决定发布，直接写前台，绕过池子、绕过后台、不产生
`decisions` 行——人事后也撤不回，因为重跑还会再写一次。

**而真正值得记下来的是第二层：这个 bug 造成的实际后果不是"错误地发布"，
是"什么都没发生"。**

`npm run export-site` 是**从池子完全重建** `data/events.json` 的。所以这个脚本
写进去的一切，都会被下一次导出静默抹掉。十五个地域版每次运行都在正常抓取、
正常判定、正常写文件，然后产出被丢进垃圾桶。池子里长期只有个位数的
経済新聞候选，不是因为没抓到，是因为抓到了扔了。

## 这个 bug 为什么能活这么久

它没有触发任何一个已有的警报，一个都没有：

- 脚本退出码 **0**
- 日志打印「published 9 条」，读起来完全正常
- `npm test` 全绿（它的单测测的是那条正则的行为，那部分确实"对"）
- CI 绿
- `lib/source-health.mjs` 管不到它——这条链路不进 `data/source-registry.json`，
  健康监测根本不知道它存在

0001 的教训是「六代平行副本让测试信号失效」。这里是同一个病的另一种形态：
**代码在跑、测试在过、日志在说成功，而产出去了一个没有人看的地方。**
上一次是信号有噪声，这一次是**根本没有信号**。

## 决定

**任何采集脚本的唯一写入口是 `lib/pool-db.mjs` 的 `upsertCandidate()`。**

具体地：

1. **采集脚本不写 `data/events.json`，不写 `data/review-events.json`。**
   这两个文件是 `export-site` 的产物，只有它能写。
2. **采集脚本不做发布判决。** 一切以 pending 落池。
   要自动判决就写 `lib/gate.mjs`，并且要过 0002 的门槛（证据事实且权威）。
3. 上面两条对**所有**采集入口生效，包括不进主管线的那些：
   `collect-shop-changes.mjs`、`collect-handmade-marche.mjs`、
   `collect-maker-faire-tokyo.mjs`、`collect-m3.mjs`、`collect-bunfree.mjs`、
   `collect-mineral-shops.mjs`。手动触发不是绕开规矩的理由。

`DISTINCTIVE` 那条正则**删掉了，没有升级成闸门规则**。判断一家店够不够
「ユニーク」是"有不有趣"的判断，0002 把这类留给人。真正事实性的部分
（开店 / 闭店 / 迁址）本来就通过 `changeType` 进后台，由 `lib/object-type.mjs`
映射成 opening / closing / place。

## 代价

`shopPublicationDecision()` 连同它的测试一起没了，短期内前台会少几条自动放行的
店铺——它们现在要等人判。这是对的：那几条本来也活不过下一次 `export-site`。

## 怎么防止复发

三道，都验证过会真实失败（不是空过）：

1. **`lib/shop-publication-policy.test.mjs` 的回归断言**：该模块的导出必须
   只有 `shopWhy`。发布判定要是又长回来，测试会红。
2. **`eslint.config.js` 的 `no-restricted-syntax` 规则**（error 级，CI 会红）：
   `scripts/collect-*.mjs` 里出现 `events.json` 字符串字面量即报错。
   只匹配字面量，所以注释里的历史说明合法、路径不合法。
3. **`scripts/collectors.test.mjs`** 覆盖 lint 表达不了的**正面要求**：
   每个 `collect-*.mjs` 都必须 import `lib/pool-db.mjs` 并调用
   `upsertCandidate()`；都不许调 `decide()` 或出现 `'published'`。
   它还先断言「至少存在 5 个采集脚本」，免得哪天目录改名后整个文件空过。

### 顺带挖出来的东西

加规则时发现仓库里有**两个 ESLint 配置**：`eslint.config.js` 与
`eslint.config.mjs`。ESLint 只读前者，后者是初版留下的死文件。
我最初把规则写进了 `.mjs`，`npm run lint` 一声不吭地照常通过——
**又一次「代码在跑、什么都没发生」**，和本记录讲的是同一个病，
只是这回发生在工具配置上。`.mjs` 已删除，`.js` 里留了注释说明。

这也顺手补了 0001 的一个漏网：那次收敛的是 `scripts/` 下的版本树，
根目录的配置文件没查。

## 附：一条可以推广的判据

**如果一段代码的产出没有落进 `data/pool.db`，那就没有任何机制能发现它失败了。**
写新采集脚本时，第一个该问的问题不是「解析对不对」，而是
**「它写到哪里，谁会因为它没写成而报错」**。
