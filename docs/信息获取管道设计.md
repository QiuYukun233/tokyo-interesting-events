# 信息获取管道设计

**日期：** 2026-08-28
**状态：** 阶段 1／2／4／6 已实施（2026-08-28），阶段 3／5 待办；第六轮新源调研（2026-08-31）已归档在末尾，尚未接入

对应方案 §3（广泛信息雷达）与 §11 阶段 1。这份文档回答一个问题：
**候选从哪来，以及为什么是这些地方。**

本文里的每个数字都是当天实测的，不是估计。探测脚本的做法记在最后一节。

## 1. 缺口有多大

当前 `data/events.json` 共 **34 条**。按开始时间拆开：

| 状态 | 条数 |
|---|---|
| 已在进行（长展期） | 17 |
| 未来 7 天内开始 | 8 |
| 8–14 天 | 1 |
| 15–30 天 | 3 |
| 更远 | 5 |

方案 §7.1 要求每轮探索队列 12–20 项，且类型必须多样。**现在的库存大约够一个人一轮**，
而且 34 条里 16 条是美术馆/大学展览，`vibe` 只有三种（奇妙体验 16 / 艺术现场 12 / 好好聊天 6）。

方案 §10 的运营漏斗设定是每周 1,000 条原始候选。**当前约每周 60 条，差约 16 倍。**

缺的不只是量，还有类别。方案 §3.2 列的六个来源家族里，我们只覆盖了三个：

| 方案 §3.2 家族 | 当前来源数 |
|---|---|
| 大型展馆与公开展会 | 1（Big Sight） |
| 艺术、设计与特殊空间 | 4（都美术馆 + 藝大三馆） |
| 大学与研究机构 | 2（东大、早大） |
| **新运动与参与式消遣** | **0** |
| 店铺生命周期 | 2（涩谷/池袋经济新闻） |
| **小型文化与亚文化** | **0** |

## 2. 实测：哪些路走得通

在设计之前先测了七条常见路径。**其中三条直觉上最该成立的，实测是死的**，
所以这一节比结论本身重要。

| 路径 | 实测结果 | 判定 |
|---|---|---|
| `schema.org/Event` JSON-LD | 8 个东京场馆站，**0 个**发布 Event 类型（Big Sight 只有 BreadcrumbList，PARCO 只有 NewsArticle） | ❌ 死路 |
| iCal `.ics` 订阅 | 东大、科学未来馆、都美术馆全部 404 | ❌ 死路 |
| `<link rel=alternate>` RSS 自动发现 | 8 个站里 0 个声明 | ❌ 死路 |
| 東京都开放数据 CSV（Big Sight） | **154 场**，14 字段含来场对象/入场费/内容/URL | ✅ 立即可用 |
| 東京都开放数据 CSV（区级） | 19 张事件表，未来 180 天内合计仅 **35 条**，多数是历史归档 | ⚠️ 低产但近乎免费 |
| みんなの経済新聞 地域版网络 | 东京圈 **15 版可达**，robots 全部允许，URL 结构完全一致 | ✅ 高性价比 |
| Tokyo Art Beat 内嵌 JSON | 单页 **1000 条**，字段最全，还带人气/收藏/到访数 | ⛔ 利用规约禁止 |

**结论一：日本的活动信息没有可利用的机器可读标准。** 想靠一个通用 JSON-LD 或 iCal
适配器一次接完几十个场馆——这条路在东京不存在。任何声称"用标准协议批量接入"的方案
都要先跑上面这个探测再说。

**结论二：真正的杠杆不在"加新来源"，而在"已有来源严重欠采"。**

## 3. 最大的两处欠采

### 3.1 Big Sight：HTML 爬到 10 条，开放数据有 154 条

我们现在用 `tokyo-big-sight.mjs` 解析 HTML 列表页，拿到 10 条。
而東京都开放数据目录里有官方 CSV：

```
https://www.opendata.metro.tokyo.lg.jp/tokyobigsight/tokyobigsighteventinformation.csv
```

Shift_JIS 编码，154 行，表头：

```
展示会名, 会期(開始), 開始曜日, 会期(終了), 終了曜日, 利用施設, 開催時間,
最終日の終了時刻, 来場対象者, 入場料について, 内容, 連絡先, TEL, URL
```

`来場対象者` 一列的分布是关键：

| 来场对象 | 场次 |
|---|---|
| 商談 | 129 |
| 商談/一般 | 13 |
| 一般 | 12 |

**25 场对一般人开放**，而我们当前从 Big Sight 只发布了 3 条。而且这 25 场正是方案
§5.2 说的那类"商谈展但值得普通人去"的东西：Maker Faire Tokyo 2026、
ジャパンレプタイルズショー、第64回全日本模型ホビーショー、日本ダーツ祭り、
COMIC CITY SPARK 21、GOOD LIFE フェア。

附带好处：`isPubliclyAccessible()` 现在靠正则匹配 `audience` 里有没有「一般」，
是启发式的；换成开放数据的 `来場対象者` 就是**主办方自己填的权威字段**。

### 3.2 みんなの経済新聞：接了 2 个版，网络里有 15 个

我们有 `shibuya-keizai-shop-changes.mjs` 和 `ikebukuro-keizai-shop-changes.mjs`
两个适配器，逻辑相同。实测东京圈可达的地域版：

```
shibukei.com          ginza.keizai.biz      shinjuku.keizai.biz   akiba.keizai.biz
roppongi.keizai.biz   koenji.keizai.biz     shimokita.keizai.biz  kichijoji.keizai.biz
asakusa.keizai.biz    shinagawa.keizai.biz  machida.keizai.biz    hachioji.keizai.biz
tachikawa.keizai.biz  nerima.keizai.biz     ikebukuro.keizai.biz
```

全部 `robots.txt` 允许，首页各约 17–31 篇文章，URL 结构统一为 `/headline/NNNN/`。

**这 13 个新版是配置行，不是新代码**——只要把现有解析器抽成一个「みんなの経済新聞」
家族适配器，注册表里多 13 条即可。这也直接补上「小型文化与亚文化」和
「店铺生命周期」两个空缺家族：这个网络报道的正是独立书店、live house、
小剧场、澡堂、模型店这类东西。

## 4. 设计

### 4.1 接入方式要可插拔

现在 `SOURCES` 的每一项都假定 `parse(html, source)`——只支持 HTML。
Big Sight 的 CSV 和区级开放数据接不进来。

改成按 `accessMethod` 分派取数器：

```
run-ingestion.mjs
  └─ fetchSourcePages(source)
       ├─ accessMethod: 'html'  → 现在的行为
       ├─ accessMethod: 'csv'   → 取字节 → 猜编码(UTF-8/Shift_JIS) → 正规 CSV 解析 → 交给 source.map(row)
       ├─ accessMethod: 'json'  → 取 JSON → source.map(obj)
       └─ accessMethod: 'rss'   → 现有 rss.mjs
```

`accessMethod` 字段注册表里**已经有了**（0002 那轮加的），现在只是没人用它分派。

两个必须内建的细节，都是实测踩到的：

- **编码嗅探**：东京都的 CSV 是 Shift_JIS，直接按 UTF-8 读会全是乱码。
  策略是先按 UTF-8 解，数 U+FFFD 替换字符，超过阈值就换 Shift_JIS 重解。
- **正规 CSV 解析**：不能按行 `split(',')`。区级数据的字段里有带引号的逗号**和换行**——
  我第一次统计町田市时数出 3091 行，正规解析后实际只有 9 行。

### 4.2 来源家族：一个解析器，N 条注册

みんなの経済新聞 15 版是这个模式的样板。注册表结构改成：

```js
{
  family: 'minkei',                    // 共用解析逻辑
  parse: parseMinkeiArticle,
  members: [
    { name: 'シブヤ経済新聞', origin: 'https://www.shibukei.com', area: '涩谷' },
    { name: '銀座経済新聞',   origin: 'https://ginza.keizai.biz',  area: '银座' },
    ...
  ]
}
```

健康监测按 member 独立计数（`lib/source-health.mjs` 已经用 `name::url` 做 id，
天然支持），所以某一个版改版失效不会被其他 14 个版的正常数据掩盖。

### 4.3 发现机制：让新来源自己冒出来

東京都的 CKAN 目录（`catalog.data.metro.tokyo.lg.jp/api/3/action/package_search`）
共 **9,658 个数据集**，其中 81 个匹配「イベント」。它是标准 CKAN，可以定期轮询：

```
npm run discover-sources   # 每周一次
  → CKAN package_search 关键词扫描
  → 与 data/source-registry.json 比对，列出「目录里有但我们没接」的数据集
  → 写进候选来源清单，等人决定接不接
```

这条不是为了区级那 35 条，是为了**新数据集出现时我们能知道**。
Big Sight 那份 CSV 就是这么找到的。

### 4.4 要申请的来源

三个源看起来是同一类问题（"去要许可"），实测下来是三个不同的问题，
**而且容易拿到的那两个恰好是没价值的**。

#### connpass —— 填表，不是谈判

- **免费申请表**：<https://forms.gle/FD6h9sKGCLXBPohZ8>（コミュニティ・個人向け）
- 认证方式 `X-API-Key` 请求头，**还必须带 User-Agent**，否则被拒
- 限流：每个 key **1 请求/秒**
- `prefecture=tokyo` 参数可直接按都道府县过滤，正合我们用
- 据社区记录，申请后约一周内邮件发 key

两个必须先知道的坑：

1. **法人不能申请免费 tier。** 条款写明「企業・法人がコミュニティ・個人向けAPIの
   利用申請を行うことはできません」，企业价是 **¥297,000/月（年付 ¥3,564,000）**。
   也就是说这个项目一旦公司化，这条线的成本从 0 跳到约 356 万日元/年。
   把它写进架构依赖之前要想清楚。
2. **禁止竞争条款**（API規約 §6.1.14）：不得用 connpass API 提供与其竞争或可能
   竞争的服务。connpass 是活动主办平台，我们是发现站，大概率不算竞争——但这是
   要自己承担的判断。

#### Doorkeeper —— 注册就有，但内容不对路

- 免费账号 → Profile 页取 **Public API Access token** → `Authorization` 头
- 限流 300 请求 / 5 分钟
- 要求**回链原活动页且不得加 nofollow**——我们本来就总是回链，天然满足
- 同样有"不得提供竞争服务"条款；内容归 Doorkeeper 及其客户所有

**robots.txt 的矛盾**：`api.doorkeeper.jp/robots.txt` 是 `Disallow: /`，
但那是对爬虫的指令；带 token 的文档化 API 是另一份契约。要用的话，
管线需要给来源加一个 `authorizedApi: true` 标记跳过 robots 校验，
并在注册表里记下依据（凭据来源、条款日期），**不能默默跳过**。

**但实测内容不对路。** 拉了默认 feed 的 25 条：

- 只有 **9 条**地址与东京相关
- 标题是「中小企業のためのSNS×AI広報セミナー」「ビーラブ２dayMG研修」
  「ロイロノート基本操作研修」这类**中小企业培训与经营研修**

顺带暴露了我们过滤器的一个真 bug：这 25 条用 `classifyActivity` 跑，
结果是 keep 17 / review 7 / exclude 1。「中小企業のためのSNS×AI広報セミナー」
命中 `signal:tech`（AI）被判成 **keep**，而它正是方案 §5.1 要排除的
"纯职业导向"内容。`HARD_EXCLUSION_RULES` 里有 `会社説明会`、`商談会`、
`セールス研修`，唯独没有 `経営セミナー`／`研修`。这条要补。

#### Tokyo Art Beat —— 唯一真正值钱、也唯一真正要谈的

它是三个里唯一命中我们主力类别（艺术展览）且量足够的源：单页 1000 条，
带 `popularity`/`bookmarkCount`/`wentCount`。但：

- **没有数据授权入口。** `/aboutEvent` 是"把你的展览投稿给我们"，
  `/aboutAd` 是买广告，都不是拿数据的路。要谈只能走一般咨询渠道。
- **利用規約 §9.1(l)** 禁止未经许可的系统性下载。在拿到书面许可之前不能接。
- **它本身是二手源**：自己从各美术馆与画廊收集，还维护一份公开的
  アートスペース一覧（展场名录）。

**因此建议：发信问，但不要等它。** 同样的艺术活动有合法的一手来源——运营方。

#### 合法的等价源：按运营方接，而不是按场馆接

东京的公立美术馆集中在少数几个运营方手里。实测 robots 全部允许：

| 运营方 | 旗下（部分） | 我们现在接了 |
|---|---|---|
| 東京都歴史文化財団 | 東京都美術館、東京都現代美術館、東京都写真美術館、東京都庭園美術館、東京都江戸東京博物館、東京芸術劇場、東京文化会館 | 只有 1 个（都美術館） |
| 国立美術館 | 国立新美術館、東京国立近代美術館 等 | 0 |
| アーツカウンシル東京 | 都内文化事业与助成项目 | 0 |

**一个運営方 ≈ 七个场馆**，而且这是一手信息、许可清楚、robots 允许。
这条路能覆盖 TAB 里相当一部分内容，不需要任何谈判。

（注：歴文財団与アーツカウンシル的 WordPress `/feed/` 存在但主 feed 是空的，
新闻在自定义文章类型里，需要找分类 feed 或直接解析列表页——尚未确认。）

### 4.5 类别缺口怎么补

「新运动与参与式消遣」和「小型文化与亚文化」两个家族目前是 0。
みんなの経済新聞 15 版能覆盖一部分（它报道 live house、独立书店、小剧场）。
剩下的需要**逐个场馆**接，没有捷径——这正是 §4.2 家族机制要省下的人力该花的地方。

### 阶段 1／2／4 实施后的实测

真正能用的库存。来源数 9 → 10（主管线）+ 15（开闭店家族）。

|---|---|---|
| 前台条数 | 34 | 68 |

### 体験100：预算估错了，而且是往贵里估错的

原本判断是「597 条，REST 载荷空，得逐条抓详情页」。实际去看之后：

- **详情页本身也是空壳**，`</main>` 紧跟在标题后面，逐条抓也拿不到日期与场馆；
- 而**列表页的初始 HTML 里字段全都在**：
  `<span class="place">` / `.date` / `.txt` / `.genre*`，链接还直接指向各馆自己的页面；
- 用浏览器看网络请求确认过**没有任何 XHR**——之前以为是 JS 渲染，
  其实是我第一次用 `<main[\s\S]*?</main>` 非贪婪正则，在第一个 `</main>` 就截断了。

结果：**12 次页面请求拿到 82 条**（每页 10 条，越界页返回 200 空列表所以固定页数是安全的），
而不是 597 次详情请求。教训是**先去看页面再估爬取预算**。

体験100 一举把最缺的类别填上了：パフォーマンス 17、こども 11、ワークショップ 7、
見学・ツアー 4、鑑賞サポート 5、歴史・伝統 4、トーク・講座 10。
同时带出了 4 个此前没有的场馆：東京都渋谷公園通りギャラリー、
トーキョーアーツアンドスペース本郷、東京文化会館、東京芸術劇場。

### 池子上限从 80 提到 300

接完之后 `mergeEvents` 的 `limit = 80` 从「供给不足」变成了「截断绑定」：
它把池子砍在一个月之外，静默丢掉了 Big Sight 尾部的文学フリマ、COMIC CITY、
模型ホビーショー。提到 300 之后覆盖完整的 180 天窗口。

**这带来一个前台问题**：`app/page.tsx` 与 `app/pool/page.tsx` 都是一次渲染整个池子，
126 条已经是很长的一页。方案 §7 的探索队列（每轮 12–20 项）本来就是解决这个的，
但它还不存在。在那之前，池子变大＝页面变长。

顺带修了一个由新数据暴露的 bug：首页的 vibe 筛选条是硬编码的三项，
而演出类内容带来了第四个 vibe「小众音乐」（15 条），那 15 条没有筛选入口。
改成从数据里推导。

## 6. 需要你决定的事

1. **TAB 要不要发信问许可。** 见 §4.4：发信成本为零，但不该阻塞任何事——
   同样的内容走運営方就能合法拿到大半。connpass 与 Doorkeeper 实测内容
   是技术勉强会与中小企业研修，与本产品不对路，**建议先不申请**。
2. **区级开放数据接不接。** 未来 180 天只有 35 条，但成本是一个适配器；
   接了以后每年会不会变多，取决于各区自己更不更新——目前看多数区已经停更了。
3. **阶段 5 的场馆名单谁来定。** 「新运动」「亚文化」这两类没有现成目录，
   需要有人按兴趣列场馆，机器帮不上忙。

## 7. 探测怎么做的

上面每个数字的来源：

- **JSON-LD / RSS 自动发现**：对 8 个场馆的列表页与详情页取 HTML，
  正则抓 `application/ld+json` 块解析 `@type`，抓 `<link type="application/rss+xml">`。
- **开放数据**：CKAN `package_search?q=イベント&rows=100`，
  逐个下载 CSV 资源，按表头是否含 `イベント名`/`展示会名` 过滤掉「公共施設一覧」
  （**这一步我第一次漏了，把 23 张设施表当成事件表，多算了约 5000 行**），
  再按 `開始日` 列统计未来 180 天内的条数。
- **みんなの経済新聞**：对 20 个候选域名取首页与 robots.txt，
  数 `/headline/\d+/` 形态的链接。
- **利用规约**：直接读 TAB 的 `/termsOfUse` §9 禁止事項。

复现这些探测不需要仓库里的代码，都是独立脚本。**如果三个月后要重新评估某条路径，
重跑探测比读这份文档可靠**——网站会变。

# 第二轮：餐饮、影视、剧本杀、手作、剧场（2026-08-28）

用户指出漏了六类：好吃的餐厅、餐厅定期菜单、新上映电影、剧本杀、拼豆手作、
音乐剧，以及"不定期但小众"的娱乐。逐个实测能不能走通，**这一节只是调研，
还没有实现任何一条**。方法和第一轮相同：查 robots.txt、查利用规约原文，
不臆测。

## 结论先说

| 品类 | 能不能做 | 靠什么 |
|---|---|---|
| 好吃的餐厅 | ✅ 能做，但有硬约束 | HotPepper グルメ Web サービス（官方免费 API） |
| 餐厅定期菜单 | ❌ 没有可规模化的渠道 | 见下 |
| 新上映电影 | ❌ 官方渠道明确禁止转载 | 见下 |
| 剧本杀 / マーダーミステリー | ✅ 能做 | 门户站点 mdms-mania.com，robots 允许、无 ToS 限制 |
| 拼豆 / アイロンビーズ | ❌ 唯一靠谱的聚合平台被 ToS 挡住 | Craftie 明确禁止未经许可的转载 |
| 音乐剧 / ミュージカル | ✅ 能做 | CoRich 舞台芸術！，robots 全开、条款未限制转载 |

三个能做，两个明确不能做，一个待续。

## 1. 好吃的餐厅：HotPepper グルメ Web サービス

官方 API，免费注册即可拿 key：`https://webservice.recruit.co.jp/register`。
`GET http://webservice.recruit.co.jp/hotpepper/gourmet/v1/?key=...`，
支持 `area`/`genre`/`keyword` 检索，`format=json` 可用。

**利用规约有三条硬约束，必须遵守：**

1. **必须署名**——页面上要明确标注数据来自 Recruit，且不能删改任何署名元素
   （包括 HTML 源码里的署名标签）。当前前台卡片没有这个位置，需要新增。
2. **不能存进"第三方数据库"，缓存要 24 小时内刷新**——这正好和我们现在的
   `data/pool.db` + 每日抓取节奏对得上（每天重抓一次，`upsertCandidate` 会刷新），
   但这条规矩意味着**不能把餐厅数据当成永久档案囤起来**，停止每日抓取的那天
   起就不能再展示。
3. **未经书面同意不能靠这个 API 赚钱**——现在站点不收费，暂时不冲突，
   但商业化之前要先联系 Recruit。

Tabelog、Retty 都明确排除：Tabelog 利用规约写明"未经同意禁止复制、转载、
保存、以营利为目的使用"；Retty 的 `robots.txt` 也把 `/API/`、
`/restaurant-search/` 这类路径专门 disallow，态度一致。**不要抓这两个。**

## 2. 餐厅定期菜单：没有可规模化的渠道

季节限定菜单这类信息几乎只存在于店家自己的官网或社交账号里，没有统一的
聚合站点或开放数据。HotPepper API 能拿到店铺基本信息但不含菜单更新。
**这条目前无解**，除非逐店接入（成本和收益不成比例），或者等 HotPepper
之类平台开放菜单字段。先搁置，不建议投入。

## 3. 新上映电影：官方渠道 ToS 明确禁止转载

映画.com 提供 iCal 公开排片表（`https://eiga.com/movie/coming.ics`），
`robots.txt` 也没有整体禁止，看起来像一条现成的路——**但页面本身的免责声明
写死了**：

> 本アプリケーション及び本アプリケーション上において表示される情報に関し、
> **個人利用の範囲を超えて、使用、複製、送信及び譲渡することを禁じます**。

翻译：超出个人使用范围的复制、传播一律禁止。这和 Tokyo Art Beat 是同一种情况——
robots 允许不代表 ToS 允许，**这条路技术上走得通、规则上走不通，不接**。

替代方案是按院线自己的官网接（TOHO Cinemas、109 Cinemas 等），实测
robots.txt 都比较宽松，但需要逐个院线写适配器，工作量和信息获取管道设计
第一轮的"运营方"模式类似——**值得做，但没有一个能一次性覆盖全部院线的入口**，
留作后续单独立项。

## 4. 剧本杀 / マーダーミステリー：mdms-mania.com

门户型媒体站，收录全国约 50+ 家马达咪丝专门店（含东京区域筛选），
`robots.txt` 只挡了 `/wp-admin/`，站点本身没有独立的利用规约页面，
没查到限制转载的条款。

这类内容的对象类型天然是 `place`（值得专程去的场所）而不是 `event`——
剧本杀店大多是常驻可预约的体验，不是按日期排的活动，这和方案 §4.1 的
`place` 分类正合适。

## 5. 拼豆 / アイロンビーズ：唯一的聚合平台被 ToS 挡住

Craftie（`craftie.jp`）是最大的手工工坊预约平台，理论上一次能覆盖拼豆、
拼贴、陶艺等一大批"参与式消遣"品类——`robots.txt` 只挡预约/管理页，
乍看能抓。但利用规约第 17 条明确写"禁止复制、转售"，第 10 条禁止未经同意
的商业使用。**规约比 robots 严，不接。**

拼豆本身在国内没有专门的聚合媒体，多是零散的品牌官方账号（如玩具反斗城
活动、東急ハンズ手作教室）或社区帖子。这条目前没有找到干净的入口，
留作后续调研——大概率要走"逐个连锁店官网"的运营方模式，和电影院线是
同一类问题。

## 6. 音乐剧 / ミュージカル：CoRich 舞台芸術！

`stage.corich.jp`，`robots.txt` 完全开放（只列了 sitemap，没有任何
`Disallow`）。利用规约通读下来只规范了"用户投稿内容归属"，**没有任何一条
限制转载演出列表数据、没有竞品条款、没有商用限制**。

实测一次请求就拿到 114 场在演/即将开演的公演，字段包括场地、地区、日期、
票价区间、剧团名——覆盖全国但可按"東京都"筛选。这是本轮里条件最干净的一个，
方案 §3.2 缺的"小型文化"里正好包括剧场，这条能直接补上。

## 关于"不定期但小众的娱乐"

这类内容本质上不是缺一个数据源，而是缺一种发现机制——展会/工坊/快闪这类
东西经常只在主办方自己的 SNS 或社区论坛里出现一次，没有聚合站点会去收录。
方案 §3.1 里的 S3/S4 层（店铺社交账号、用户投稿）就是为这类内容设计的，
但目前的管线完全没有覆盖到这两层。这不是"再加一个适配器"能解决的问题，
需要先设计一条"人工线索 → 待核实池"的输入通道（方案 §3.1 S4 层的雏形），
比六个具体品类的调研工作量更大，值得单独讨论要不要做。

## 下一步需要你定的事

1. **HotPepper 要不要接？** 能做，但要先在卡片上加官方要求的署名展示，
   且要接受"数据不能囤超过 24 小时"这条约束（和现在的每日抓取节奏刚好吻合，
   不是新增负担）。
2. **CoRich 和剧本杀门户先接哪个？** 两条都干净，工作量和 Big Sight/rekibun
   接入相近（一个适配器 + 注册）。
3. **电影院线、拼豆连锁店要不要走"逐个运营方接入"？** 工作量比前面几条大，
   而且现在还没验证过哪几家院线/连锁店的 robots 和 ToS 真的允许。
4. **"小众不定期"要不要单独设计一条人工投稿/线索通道？** 这是本轮里唯一
   不是"加个来源"就能解决的，需要先讨论产品形态。

# 第四轮：中古店与小众店铺的发现方式——展会出展者目录（2026-08-28）

## 结论先说

你提的思路成立并且已经落地：**展会/フェア自己的出展者目录，是发掘小众个人
店铺/创作者最有效的入口之一**——不用一个个找店，展会已经把一批同类小店集中
在一份结构化名单里了。这个思路你自己又做了一次推广：不局限于古董/中古，
任何靠展会获客的小众业态都适用；同时提出可以考虑博主的体验谈作为另一种
补充渠道（评估结论见下）。

## 摸了哪些展会

按"临近开展、目录大概率已填充"为标准筛选（这个条件和展会知名度/规模无关，
每个展会要单独查）：

- **Maker Faire Tokyo**：已验证可行且条件比手作市集更好——`robots.txt` 是
  普通默认设置，没找到限制转载的利用规约页；50 音索引页 14 页就能列出
  2026 届全部约 290 个出展者（手作市集要按品类页凑数量，还没有出展者名字），
  且每个出展者的展期是全场固定两天，不用像手作市集那样逐行解析出展日。
  赞助商展位（`SPONSOR` 标签）要不要收进候选池明确问过你，答复是"都收进来，
  留给后台判"。**已实现**，见 `scripts/sources/maker-faire-tokyo.mjs` +
  `scripts/collect-maker-faire-tokyo.mjs`。
- **東京ハンドメイドマルシェ**：已验证可行，`robots.txt` 明确点名 ClaudeBot
  为"意图性允许"（AEO 方针）——和 fmfm.jp 明确拉黑同一批爬虫正相反，是这轮
  探测里第一次遇到主动欢迎的站点。**已实现**，见
  `scripts/sources/handmade-marche.mjs` + `scripts/collect-handmade-marche.mjs`，
  以及 `docs/来源清单.md`「手动/偶发触发来源」一节。
- **Design Festa**：部分验证——出展检索功能存在，但没能确认长期稳定可查，
  留作后续候选，不在本轮实现。

## 博主体验谈：评估为"形状不对"，先不做爬虫

珍スポット/独特娱乐体验谈类博客是长文叙事而非结构化的时间地点信息，
适合当编辑参考读（找灵感、找下一批要摸的小众品类），不适合做成抓取源。
如果之后要用，应该走 `data/manual-events.json` 的人工整理路径，不是爬虫。

## 手作市集的实现要点

出展者列表页（`/creators/list_creators/?genre=<id>`）只给 `exhibitor_id`，
真正的字段在各自的详情页上——一次完整抓取是"品类数+出展者数"次请求，
一届约 700 次，这是它做成独立手动脚本、不进每日 cron 的原因（另见
`docs/架构.md`「展会出展者目录是第三条链路」）。品类列表故意排除了
官方展位（公式ブース/PRブース），因为那不是独立创作者的内容。

用真实抓到的 4 个创作者详情页 + 1 个品类列表页验证过解析逻辑，全部正确。

# 第五轮：非 toB 中大型展会的垂类地图（2026-08-28）

这一轮不是为了立刻实现，是**先摸清有哪些有趣的垂类**。五路并行调研
（同人二次元 / 生物矿物自然 / 收藏嗜好 / 食饮民族 / 艺术学术），

## 最重要的三条结论

### 1. 场馆催事日历是发现新展会的元入口，成本极低

与其逐个猜展会名字，不如去读场馆自己的催事日历。实测：

### 2. 「出展招商制」才产出名单，「厂商直销制」不产出

这是判断一个展会值不值得写 parser 的**第一道筛子，比规模和知名度都更有预测力**。

- 招商制（有出展者一覧）：文学フリマ、M3、ワンフェス、博物ふぇす、とんぶり市…
- 直销制（无名单）：鉄道部品即売会（JR 各支社自办）、大江戸骨董市、旧車天国、
  痛車天国（参加者是"车主"不是"出展者"）

后者的亚文化圈真实且有趣，但**只能当一条事件收录，不能拆成 N 条参展方候选**。

### 3. 主办方「基因」可迁移，一个 parser 可以吃掉多个展会

手紙社系（紙博・布博・東京蚤の市）共用同一套模板：静态 HTML、结构化字段、
robots 友好。同理 アクアリウムバス / アクアリウム東京 也同模板。
**验证一个主办方 = 拿下它旗下全部展会**，比逐个展会调研杠杆高得多。

反例见下面「代々木公園民族フェス」——同一场地、同一形态，却因为主办方各自
独立而毫无共性。**共性来自主办方，不来自场地或品类。**

### 对前面「场馆催事日历」一节的补正

**東京ビッグサイト 不只是 168 件的当月列表，有可回溯到 2009 年的检索接口**：

```
POST https://www.bigsight.jp/visitor/event/search.php
  negotiation_ja=2      # 1=全て 2=一般 3=商談
  target_year=2016      # 下拉可选 2009〜2027
  target_month=8
  submit=target_search  # ← 缺这个参数筛选静默失效，返回默认结果
```

分页 `GET /visitor/event/search.php?page=N` 需带 POST 后的 cookie 保持筛选状态。
实测 `2016/8 一般` 24 件、`2009/8 全て` 15 件。
**一般公開约 170 件/年 × 17 年 ≈ 2,500 条历史候选**，每条自带主办方官网外链。

**産貿中心是纯前瞻日历，无档案**：向前约 10 个月（2027/6 仍有数据），
过去月份一律返回 0 条。2026/9–12 四个月两馆合计 150 件（公開 97），
约 290 件公開/年。字段里 `公開 / 招待 / 関係者のみ` 与 7 级 `category`
都是现成的 gate 信号。注意 URL **不要加尾斜杠**。

**幕張メッセ**：列表分页是 JS `pager(N)` 无 URL 参数，但
`/event/detail/{id}` 连号可枚举，字段含 `対象者（関係者/一般）+ 入場料`。
robots 404。千叶不在都内，中优先级。

**三个新确认的负面结论**（逐链接枚举后确认，不是没找到就下结论）：
**東京流通センター（TRC）**、**大田区産業プラザ PiO**、**浅草橋ヒューリックホール**
均不公开催事日历。TRC 站方明说空室状况只通过邮件杂志发送。
→ 覆盖这两个场馆的**唯一途径**是下面的聚合站；聚合站不是"补充"而是唯一入口。

### 即売会聚合站（覆盖 TRC/PiO 的唯一入口）

**ケットコム** `ketto.com`（since 2000）——同人即売会情报站，覆盖 TRC、PiO、
区民会館这一整层小场地。字段独一份：`ジャンル`（细到「TIGER&BUNNY 虎徹受けオンリー」
「超かぐや姫ONLY」）、`属性タグ`（[コス可] [女装可] [お茶会] [撮影セット]）、`〆切日`。
三个工程要点：**Shift_JIS**；**CGI 端点直接 GET 返 500，加 `Referer` 头才 200**；
robots **没有 `User-agent: *` 条目**（只逐条封具名 bot），但 **CCBot 在封禁名单里**
——字面上我们不受限，但说明站方对 AI 爬虫有戒心，UA 绝不能自称 AI 爬虫名且必须严格限速。

**赤ブーブー通信社** `akaboo.jp/event/` —— 652KB 单页静态一次拿完，
**1,414 个详情页链接、页内「オンリー」出现 473 次**。字段含每场併催オンリー的
`ジャンル / 参加費 / 締切日 / 一般入場有料無料 / コスプレ可否`。robots 404。
与 ケットコム 互补：akaboo 是赤ブー自家大会的第一手数据，ケットコム 覆盖第三方小型 ONLY。

**ハンドメイドマルシェ 全国一覧** `handmade-marche.jp/list/` —— **这是已实现来源的兄弟**。
同一运营方在全国办 9 场：東京（プリズムホール 700 ブース）、**ヨコハマ（パシフィコ横浜 2,500 ブース）**、
小倉、金沢、静岡、京都、浜松、名古屋、札幌。各场次官网同样有
`ハンドメイド出店一覧 / フード出店一覧 / 体験教室` 三个名录页。
**`scripts/sources/handmade-marche.mjs` 的解析器应该可以直接复用**，
横滨单场 2,500 摊就顶现有候选池近十倍。这是本轮性价比最高的一条。

**ものづくり応援団** `tedukuriichi.com` —— 全国手作り市，
`index.php?mono=event&event_id={N}` id 已到 3000+ 可枚举。

### 必须写进管线的约束（都是实测踩出来的）

1. **UA 绝不能自称 ClaudeBot / GPTBot / CCBot / Google-Extended。**
   東大两站、工大祭、多摩六都、ケットコム 都逐条封这些名字，
   而 `User-agent: *` 是放行的。**用项目自己的标识 UA 即合规。**
   東大站点还带 `Content-Signal: use=reference`（允许引用式使用）
   ——"摘要 + 回链主办方"正是它允许的用法。
2. **robots 解析的两个陷阱**，`run-ingestion.mjs` 都要按"无限制"处理：
   **soft-404**（`isas.jaxa.jp/robots.txt` 返回 200 但内容是 HTML 404 页）、
   **真 404**（bigsight / akaboo / m-messe / miraikan / mitasai / geisai / nao / riken 全部无 robots.txt）。
3. **来源必须分「常年」/「年度」/「季节性」三类。** 五月祭、駒場祭、藝祭、
   サイエンスアゴラ、各研究机构一般公開在 off-season 全是零产出或空响应。
   `check-sources` 若不区分，一年会红 10 个月——**这会重演 0001 的"测试信号失效"**。
4. **著作权分档**：宽松可摘要（NAOJ 明列 SNS 发信自由需 credit、JST、AIST、
   文学フリマ 条款明写会被转载、TABF 无条款）；**严格只取事实字段+回链**
   （一橋祭、三田祭、五月祭第6条、理研）；**禁 frame 嵌入**（五月祭、一橋祭、
   サイエンスアゴラ、理研、AIST）；**禁图片直链**（KEK）。
   駒場祭「情報指針」还要求信息变更时同步修正或删除，并**建议事前向委员会告知发信内容**
   ——发一封说明邮件是低成本的合规动作。
5. **软 404 / catch-all 陷阱**：`koganecho.net` 任意路径都返 200、
   `chofusai.jp` 往届字节数与首页一致——**不能靠 HTTP 状态码判死链，要校验内容**。
6. **单页体积**：TABF 2.7MB、文学フリマ 1.6MB、akaboo 652KB、科博 JSON 31MB。
   **测试夹具必须截片段**，别把整页塞进 `.test.mjs`。
7. **编码**：`ketto.com` 与 `psj.or.jp` 是 Shift_JIS；`ketto.com` 的 CGI 必须带 Referer。

### 量级预警：接之前先写规则

若把两侧第一梯队都实现，一轮全量约 **9,000+ 条**（场馆/聚合侧 3,000+、
展会侧 6,000+）。相对当前池子，这是两个数量级的推进，已知问题 #4 的
"每周 1,000 条"目标可达——**但会立刻把已知问题 #1（候选积压等人判）推到临界**。

好在这批来源自带现成的权威规则信号：
**Big Sight 的 `入場区分`（商談/一般）、産貿センター 的 `公開/招待/関係者のみ`、
五月祭/駒場祭 的 `cautions.flags.{ticket, reception, restrictedEntry}`**。
这些都是主办方自己声明的事实，符合 0002 对规则的要求（事实性、权威、非 taste）。
**建议在接入这些来源的同一个提交里就把对应 `rule:` 写进 `lib/gate.mjs`，
而不是先灌池再回头补规则。**

## Design Festa：三条独立证据确认 web 上没有出展者名单（2026-08-28 复核）

这条来源前后被记过三次不同的状态（"部分验证"→"名单已迁到 App"→本次复核），
所以把证据写全，免得再有人从头查一遍。**结论是确定的：不接。**

规模上它本该是最诱人的一个——约 6,500 ブース/日、年 2 回、東京ビッグサイト，
下一届是 vol.64。障碍不在 robots（`Disallow: /wp-admin/` 而已），
而在于**名单根本没有发布到 web 上**。

三条独立验证：

1. **`wp-json/wp/v2/types` 里根本没有出展者类型。** 全部 post type 是
   `post / page / attachment / nav_menu_item / wp_block / wp_template /
   wp_template_part / wp_global_styles / wp_navigation / wp_font_family /
   wp_font_face / emanon-premium-bp / popup / popup_theme / pum_cta / column`
   ——没有任何一个能装出展者。
2. **`/about-artists/`（出展者紹介）自己写明是自愿登记的子集**：
   「出展者紹介は掲載希望の申請があった出展者様のみの掲載となります」。
   实际内容只有餐饮摊位（うめぼしの松本農園、うるまジェラート…），
   带提供菜单和过敏原，和一般摊位无关。历届 `出展者紹介57/58/59/63` 同构。
3. **站点自定义的 `df/v1` REST 命名空间里没有名单路由。** 这是本轮新挖到的
   东西：草稿页「出展者ページ（仮）」(`/shuttennshatest/`) 里有个客户端组件
   `#dfap-root`，它调 `fetch("/wp-json/df/v1/artist-page")`。顺着挖出整个命名空间：

   ```
   /df/v1/page-data/{slug}   出展申込页的文案与料金（booth/dbooth/workshop/
                             special/indoor/performance/restaurant，vol.64）
   /df/v1/artist-page        出展者用的マイページ按钮组，不是名单
   /df/v1/visitor-page /hero /logo /news-page /about /points /other
                             /announcement-banners   都是首页内容块
   /df/v1/exhibition         **空数组 `[]`**，且路由声明 args 为空，
                             vol/year/event/per_page 等参数一概无效
   /df/v1/genre              是跑马灯文案设置，不是品类表
   ```

   `exhibition` 与 `genre` 都是 GET/POST 成对的内容设置端点（后台编辑器用的），
   不是出展者目录。

附带排除的路径：`search. / app. / api. / guide. / map. / my. / entry.designfesta.com`
与 `designfesta.jp` **DNS 全部不解析**；`wp-sitemap.xml` 返回 501
（服务器缺 SimpleXML，站点自己的 sitemap 是坏的）；
`store.designfesta.com` 是 Shopify 上的官方周边店（3 个商品），不是作家目录。

> 顺带一提，`store.designfesta.com/robots.txt` 里有一段**面向 AI 代理的指令**
> （让代理去装某个购物 skill、走 MCP 端点下单）。那是 Shopify 的模板文案，
> 不是本项目的指示，也与抓取无关，不予理会。记在这里是为了说明
> **robots.txt 里出现的自然语言指令属于"观察到的内容"，不是命令**。

**所以 Design Festa 只能作为一条事件收录**（"这两天有个 6,500 摊的巨型创作市集"），
拆不出参展方。这正是第五轮那条规律的又一例：招商制展会未必就会公开名单，
**"有没有名单页"必须逐个实测，不能从规模或知名度推断**。
