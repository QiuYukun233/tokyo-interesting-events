## 开闭店与小型文化（`npm run collect-shop-changes`）

みんなの経済新聞ネットワーク，**15 个东京圈地域版共用一个适配器**
（`minkei.mjs`），robots 全部允许：

```
シブヤ / 池袋 / 銀座 / 新宿 / アキバ / 六本木 / 高円寺 / 下北沢
吉祥寺 / 浅草 / 品川 / 町田 / 八王子 / 立川 / 練馬
```

两段式：抓一次首页取开闭店线索，再只抓命中的文章页。超过 45 天的线索丢弃。
这个网络报道独立书店、live house、小剧场、澡堂、模型店，同时补上方案 §3.2 的
「店铺生命周期」与「小型文化与亚文化」两个家族。

判定在 `lib/shop-publication-policy.mjs`；涩谷版沿用它自己更早的策略，
其余 14 版共用一条规则，直到有证据要分开。

**CoRich 没有可用的查询参数过滤。** `category_id`/`pref_id` 在 GET 请求上不生效
（实测每个 `category_id` 都返回同样的未过滤总数），只能整页抓下来，
按每条自己的 `.theater .pref` 文本判断是不是东京都。这也意味着**没有按类型
过滤**——演剧、音乐剧、落语、能楽、2.5次元舞台混在一起，这是刻意的：
方案 §3.2「小型文化与亚文化」要的就是这种长尾，不该在抓取阶段就按"像不像
主流剧场"筛掉。

**SCRAP 分两种页面模板，且只接了 3/6 家东京店。** 池袋・吉祥寺共用一套
`ul.list02` 模板（域名 scrapmagazine.com），東京ミステリーサーカス（新宿）
是完全不同的 `article.js_eventsItem` 模板（域名 mysterycircus.jp）。
另外原宿・浅草・渋谷三家店挂在 `realdgame.jp`，那个域名的 `robots.txt`
里 Sitemap 指向一串像是被 SEO 插件污染过的乱码文件名，先不碰——不是技术
做不到，是信号不干净。

**SCRAP 有常驻不设结束日期的游戏，会随时间推移悄悄跌出可见窗口。**
现有的"无结束日期＝单日活动"假设第一次撞上"无结束日期＝长期常驻"，
候选会被正常抓到、正常入池，但 180 天窗口一过就从 `/backstage` 和
`npm run review` 里消失，即使这个游戏其实还能订。这是对象模型本身的
缺口，见 `scripts/sources/scrap.mjs` 里的注释，没有强行打补丁。

**吉本兴业用的是内部 feed API，不是网页。** 排期页面本身是 JS 异步渲染的，
真正的数据来自 `feed-api.yoshimoto.co.jp/fany/theater/v1`——从官网自己的
`event.js` 里读出来的调用方式，无需鉴权。这台主机自己的 `robots.txt` 返回
的是 API 网关鉴权错误（403），说明它本来就没打算被当成"网页"看待，
无所谓允不允许爬。这条经过 2026-08-28 明确确认后使用，且约定按现有的
"每天一次"节奏跑，不额外加频率——4 个东京剧场每次抓取各一次请求，
±60 天窗口，和官网自己一次页面加载请求的量级相当。

## 场馆催事日历：和其他来源不是一个形状

**東京都立産業貿易センター 台東館 / 浜松町館（`sanbo.mjs`）** 是第一条
**场馆日历型**来源，和其余所有来源的形状不同：别的来源是「某个主办方自己的
活动」，这条是「**任何人订了这个厅之后要办的事**」。

这两个馆是东京小型即売会的物理枢纽——爬虫類、アクアリウム、小動物、鳥、
昆虫、手作り、書道 全在这儿办，主办方大多小到不值得为它单写一个适配器，
而且基本搜不到。读场馆日历一次就能全覆盖。文档第五轮里那条
「爬虫・奇蟲・珍獣フェア!!」就是这么捞出来的，五路关键词搜索都没搜到过。

两个字段让判断变得异常便宜，且都是**场馆自己的登记记录**而非任何人的猜测：

| 字段 | 取值 |
|---|---|
| `区分` | 展示会・見本市 / イベント / **即売会** / 会議・研修・セミナー / 展覧会・発表会 / 試験・審査・競技 / 就活関連 |
| `公開区分` | **公開 / 招待 / 関係者のみ** |

后者映射到 `audience`，由 `lib/gate.mjs` 的 **`rule:not_open_to_public`** 判决
——和 Big Sight 的 `来場対象者` 驱动 `rule:trade_only_admission` 是同一类证据：
场馆记录的「能不能进」，不是「有不有趣」。**没有徽章的行保持 pending**，
因为「没写」不是一种声明，安全的读法是「该有人看一眼」而不是「不开放」。

日历只朝前看：过去的月份返回 0 条，向前约 10 个月。**没有归档**，所以每日
重抓不会丢东西，`sanboUrls()` 走一个滚动的 12 个月窗口。末尾几个空月份是
正常的，不是解析器坏了。

两个实现上的坑：

- **URL 不能带尾斜杠**（`/taito/event?year=…`），站点自己的链接就是这么写的。
- **非公开条目也有 `<a>`，但 href 是 `javascript:void(0)`**。当成链接会产出
  一堆 sourceUrl 字面等于 `javascript:void(0)` 的候选。只认 `/event/<数字>`
  形式的路径，其余回落到月历页。

`robots.txt` 是 `User-agent: * / Disallow:`，全站放行（2026-08-28 确认）。

首轮实测：两馆 12 个月窗口共 **80 条**（台東館 36 · 浜松町館 44），其中即売会 19、展示会・見本市 19、
イベント 25、就活関連 8；`招待` 9 + `関係者のみ` 8 共 17 条被新规则判掉。

**東京ビッグサイト 没有再接一遍。** 它的 HTML 检索接口能回溯到 2009 年
（见 `docs/信息获取管道设计.md` 第五轮补），但那是**已经办完的**展会，
对候选池没有意义；未来的场次现有的开放数据 CSV 已经覆盖，且 CSV 的
`来場対象者` 比 HTML 更规整。那个历史接口的价值是**调研时用来发现垂类名字**，
不是入池，所以没有做成适配器。

## 手动/偶发触发来源（不在每日 cron 里）

某些来源绑定的是现实中周期性举办的展会，不是每天都有新数据——展前几个月
出展者页面是空的，展会结束后目录也不再更新。挂进 `scripts/sources/index.mjs`
的每日 `SOURCES` 只会带来几百次徒劳的重复请求，所以这类来源做成独立脚本，
临近展期手动跑一次。

**東京ハンドメイドマルシェ（`scripts/sources/handmade-marche.mjs` +
`scripts/collect-handmade-marche.mjs`）** 是用户提出的「展会出展者名单」思路
的第一个落地：小众个人创作者店铺普遍靠展会获客，展会自己的出展者目录就是
一份现成的、结构化的店名/品类清单，比逐个找小众店铺的独立官网高效得多——
这个思路不限于古董，任何靠展会获客的小众业态都适用。

结构上：真正的字段（创作者名、品类标签、展位号、出展日、SNS 链接）只在
各自的 `/creators/?exhibitor_id=<id>` 详情页上，列表页只给 `exhibitor_id`。
所以一次完整抓取是「列表页数 + 出展者数」次请求，东京一届约 760 次——
这正是它不能进日常 cron 的原因。

> **⚠️ genre 参数的坑（2026-08-28 修，曾经真的丢了 93% 的数据）**
>
> `/creators/list_creators/?genre=<id>` 看起来是按品类分页，会返回像模像样的
> 约 49 条，所以第一版实现就去遍历品类再取并集。**实际上 `genre` 参数在缺少
> 表单的 `s` 标记时被完全忽略**：每个品类返回的都是同一批 49 条，全部品类的
> 并集还是那 49 条——而东京一届真实有 **722** 个出展者。
>
> 这和 CoRich 的 `category_id` 是同一类坑（见下文「CoRich 没有可用的查询参数
> 过滤」）：**筛选参数被接受、什么都不改变、还返回足够多的行让你以为它生效了。**
>
> 带上 `?s=` 检索才真正执行，并按 20 条分页。所以现在的发现逻辑是走
> `?s=&page=N` 完整翻页、**完全不带品类筛选**——比坏掉的品类循环请求数更少，
> 而且拿得全。翻到空页即结束。采集脚本还会把走下来的条数和页面自报的
> 「全 N 件」对账，不一致就告警——这个 bug 当初就是因为没有对账才藏住的。

这也顺带废掉了原先那份手工维护的品类清单（曾经故意排除 90 公式ブース /
91 PRブース、保留 92 キルト出店エリア）：既然不再按品类发现，就不需要它了。

**同一运营方在全国办 10 场，每个城市一个子域，共用同一套 HTML**
（`handmade-marche.jp` 本身是横滨场，其余是 `tokyo.` `knz.` `kkr.` 等子域），
所以一个解析器覆盖全系列，`--site` 选城市。规模差别很大：东京 700 摊，
**横滨 2,500 摊**，札幌 1,200，名古屋/小倉/金沢 各 1,100。
**默认只跑东京**——跑不跑东京以外的场次是"这个站的地理边界到哪"的产品决定，
必须显式指定，代码不替你做主。

`robots.txt` 明确点名 ClaudeBot 等 AI 爬虫为「意图性允许」（AEO 方针，2026-08-28
确认）——和 fmfm.jp 明确拉黑同一批爬虫正相反。

用法：`node scripts/collect-handmade-marche.mjs --site tokyo --year 2026`，
临近每届展会手动跑。

**Maker Faire Tokyo（`scripts/sources/maker-faire-tokyo.mjs` +
`scripts/collect-maker-faire-tokyo.mjs`）** 是同一个思路的第二个来源，条件
更好：`robots.txt` 是普通的默认设置（只挡 `/wp-admin/`），没找到限制转载的
利用规约页；发现成本也低得多——50 音索引页（`?n=101..114`）14 页就能列出
2026 届全部约 290 个出展者，而且**索引页的分页是真的按索引分片，不像手作市集
那个假的 genre 参数**。每个出展者的展期是全场固定的两天，不像手作市集要按行
解析单独的出展日，字段直接来自 `source.startDate`/`endDate`。

赞助商展位带 `SPONSOR` 标签，但和其他出展者一样有自己的品类标签、简介、
展位号——**明确问过是否要排除**，答复是"都收进来，留给后台判"，
所以抓取阶段不做任何过滤。

用法：`node scripts/collect-maker-faire-tokyo.mjs --start 2026-09-05 --end 2026-09-06`，
临近展期（2026 届为 9 月 5-6 日）手动跑。

**M3（音系・メディアミックス同人即売会，`scripts/sources/m3.mjs` +
`scripts/collect-m3.mjs`）** 是同人音乐即売会，一年两次在東京流通センター，
约 1,700 个社团卖自己录的作品。**接它的理由是它的品类表**——レトロゲーム音楽、
音ゲー、東方project、VOCALOID、ドラマ・トーク（放送劇・声優）、実験映像
是**主办方声明的独立分类**，不是谁猜的标签。这正是方案 §3.2 要的长尾，
而且这些东西在任何场馆日历上都不会出现。

前台是 Next.js SPA，但它读一个**公开无鉴权的 REST API**，比爬渲染后的页面好得多：

| 端点 | 内容 |
|---|---|
| `GET /exhibitions` | 全部届次，`isActive` 标出当前届 |
| `GET /exhibitions/{id}` | 该届的 `eventDate` |
| `GET /circles/{id}` | **约 1,700 个社团一次全量返回**（1.5MB） |
| `GET /companies/{id}` | 企业出展（没有采集——这里要的是个人社团的长尾） |

**两个字段让候选卡片不需要我们编任何理由**，且都是社团自己写的：
`prText`（自我推介全文）与 `keywords`（自填标签）。实测 1,741 条里
**品类和自述 100% 覆盖，97% 带自己的官网或 SNS**。

品类码表（21 个）是从它列表页 SSR 出来的 `<select>` 里抽的——API 只返回
`A14` 这样的裸码，且没有码表端点。**未知码原样透传而不是丢掉**，
这样新增分类会以它自己的样子出现，而不是凭空消失。

`eventDate` 是 `2026-04-24T15:00:00.000Z` 这种形式，**按 UTC 读会少一天**
（15:00Z 正好是 JST 次日零点），必须按 Asia/Tokyo 折算。

### 为什么它是独立脚本而不是日常来源

不是因为成本——一次全跑只要 3 个请求。是因为**届次 id 算不出来**，
必须先查 `/exhibitions`，而注册表的日常来源用的是模块加载时就固定的 URL 列表。
写死 `/circles/2026s` 的后果是：展会过去之后它仍然返回那一届完整的 1,700 行
——响应看着满满当当、不报错、不触发 `empty_parse` 告警、而且再也没有新东西。
这正是第五轮警告过的**季节性来源的静默失效**，所以届次改成运行时解析。

同样的道理还加了一道**过期守卫**：两届之间 API 会一直把上一届标成 active，
这时候直接跑会把约 1,700 条**已经办完、永远不可能发布**的候选灌进本来就在
积压的待判队列（已知问题 #1）。所以解析出的日期早于今天就拒绝执行并说明原因，
要回填旧届次得显式加 `--allow-past`。

三个主机都没有 robots.txt（404），无限制；目录本来就是发布给来场者查阅的。
2026-08-28 确认。

用法：`node scripts/collect-m3.mjs`（自动选当前届）或 `--edition 2026s`。

**文学フリマ東京（`scripts/sources/bunfree.mjs` + `scripts/collect-bunfree.mjs`）**
是文艺自出版即売会，约 3,200 个出店者、東京ビッグサイト、一年两次。
接它的理由是**品类词表**：出店者从主办方的两级分类里自己挑，
`詩歌|現代詩・散文詩`、`小説|妖怪・もののけ`、`評論・研究|建築・都市計画`、
`評論・研究|郷土`——长尾已经被做东西的人自己标好了。

`/c/{届次}/all/50` **一个请求渲染全部出店者**（1.6MB），每行给
ブース / 出店名 / 详情链接 / 品类。届次的日期、场地、正式名都从页面
`<meta name="description">`（形如「「文学フリマ東京42」(2026/5/4、東京ビッグサイト) の
全出店者リストです。」）里读，不用硬编码。各出店者的详情页（紹介文・SNS・販売物）
要再花约 3,200 个请求，**故意不抓**。

实测 42 届：3,237 条全部解析、id 无碰撞、品类 100% 覆盖。

### 三条访问限制，逐一实测（2026-08-28）

同一台机器、同一 IP、同一时刻：

| 客户端 + UA | 结果 |
|---|---|
| `curl` + 项目 UA | **200** |
| `curl` + 空 UA / `curl/8.0` / 裸 `Mozilla/5.0` | 403 |
| **Node `fetch` + 项目 UA** | **403** |

1. **存根式 UA 被拒。** 不需要伪装浏览器，只是不能发空的或库默认的 UA。
2. **境外 IP 被拒，且是站方明文政策。** 利用規約：「不正アクセス防止の観点から、
   日本国外のIPアドレス・匿名プロキシ・匿名VPN (Tor など) 等を経由した通信…
   を自動的に遮断する場合があります」。**所以这条来源不能进 CI**
   ——GitHub Actions 的出口在境外。这是要遵守的，不是要绕的。
3. **Cloudflare 按客户端指纹拦截。** UA、IP、时刻全都一样时 curl 200 / Node 403，
   差别只在 TLS/HTTP 客户端指纹。

第 3 条的处理经过明确确认后定为：**用 `curl` 子进程发请求**
（`scripts/lib/curl-fetch.mjs`，一个 fetch 形状的薄封装）。
边界写在那个文件的注释里，这里重复一遍要点：
**我们仍然发送项目自己的诚实 UA，不伪装浏览器；robots 与站方明文规则全部遵守
（包括不绕境外 IP 限制）。curl 只是另一个正规 HTTP 客户端。
伪造浏览器 TLS 指纹是另一回事，本仓库任何地方都不做。**

robots 允许 `/c/`（只禁 `/anonymous /admin /api /error /payment /legal`），
另外逐条封了一长串具名 SEO/归档爬虫，我们不在其中。
利用規約 §3 反而写明投稿内容可能被转载到其他站点，没有禁止抓取的条款。

### 两道守卫

- **未公开的届次会 302 跳回目录首页**，跟随重定向会把它解析成"空展会"。
  所以请求用 `redirect: manual`，检测到 3xx 就报"该届名单尚未公开"并退出。
  实测 `tokyo43` 正是这个状态。
- **过期届次的名单仍然可访问**，直接抓会把三千多条已经办完、永远不可能发布的
  候选灌进本来就积压的待判队列。日期早于今天就拒绝执行，要回填得显式
  `--allow-past`。与 `collect-m3.mjs` 同一条规矩。

用法：`node scripts/collect-bunfree.mjs --edition tokyo43`，从日本网络跑。

## 已知的坑

**早稲田大学的 robots.txt 取不到（已解决，但留个说明）。**
`https://www.waseda.jp/robots.txt` 返回的是 Cloudflare 的 403 挑战页，换任何
User-Agent 都一样（含空 UA 与浏览器 UA），而活动列表页 `/top/event/list` 对我们的
UA 正常返回 200。所以这个站**没有可取回的 robots.txt**，不是它禁止了我们。

此前管线按"非 2xx 即拒抓"处理，把这个来源整个丢掉了。现在按 RFC 9309 §2.3.1 办：
4xx 表示 robots.txt 不可用、可以访问；429 与 5xx 表示答案未知、不抓。
但**非 404 的 4xx 会在注册表里记 `robots_unavailable` 警告**——放行是明面上的，
不是悄悄的。

如果哪天早稲田的 robots.txt 变得可读且写了 Disallow，管线会自动改回拒抓，
不需要改代码。

**Big Sight 的公开性判定仍然只看一个字段。** `isPubliclyAccessible()` 检查
`audience` 是否含「一般」。换成开放数据后这个字段变成了主办方的权威声明，
比原来的正则猜测可靠得多，但方案 §5.2 的五条保留条件（能否合法报名、
是否要求虚构身份、现场有无实体展示等）仍然一条都没实现。

**`audience` 字段有两套语义。** Big Sight 用它表示「谁可以来」，
而 `utokyo-events.mjs` 用它装「オンライン」「本郷地区」这类地点/形式。
目前 `isPubliclyAccessible()` 只作用于 Big Sight 所以没有实际冲突，
但这是个契约隐患。

**藝大三个馆共用 `source` 字段。** 三条来源同名，前台无法区分，只能靠 `place`。
注册表里靠 `name::url` 组成的 id 区分，所以健康监测不会把它们混在一起。

## 加一个来源要做的事

1. 先看 `robots.txt` 与使用条款。
2. 在 `scripts/sources/` 建 `<来源>.mjs`，导出 `parse<来源>(html, source)` 和 URL 常量；
   用 `createEventCandidate()` 造记录。
3. 同目录建 `<来源>.test.mjs`，**用内联 HTML 夹具**，不要打网络。
4. 注册进 `scripts/sources/index.mjs`，**填对 `accessMethod`**
   （`html` 用 `parse(html, source)`；`csv`/`json` 用 `map(record, source, index)`，
   取数与编码嗅探由管线负责），并填全方案 §3.3 的字段：`sourceFamily`、
   `trustTier`、`accessMethod`、`crawlFrequency`、`expectedUpdateWindowDays`、
   `robotsAndTermsCheckedAt`、`parserVersion`、`ownerOrContact`。
   **改解析器时同步改 `parserVersion`**——它是重写之后用来定位"该复查哪些来源"的东西。
5. 跑一次 `npm run update-events`，再跑 `npm run check-sources` 确认没有告警，
   把原始条数补进上面的表。
6. **不要新建 `index-v2.mjs`。** 见 `决策记录/0001-收敛版本树.md`。
