## 开闭店与小型文化（`npm run collect-shop-changes`）

みんなの経済新聞ネットワーク，**15 个东京圈地域版共用一个适配器**
（`minkei.mjs`），robots 全部允许：

```
シブヤ / 池袋 / 銀座 / 新宿 / アキバ / 六本木 / 高円寺 / 下北沢
吉祥寺 / 浅草 / 品川 / 町田 / 八王子 / 立川 / 練馬
```

两段式：抓一次首页取开闭店线索，再只抓命中的文章页。超过 45 天的线索丢弃。
这个网络报道独立书店、live house、小剧场、澡堂、模型店，同时补上方案 §3.2 的
「店铺生命周期」与「小型文化与亚文化」两个家族。

**这条链路 2026-08-28 重写过，之前它是坏的。** 它原本读 `data/events.json`、
把自己挑中的合并进去再写回——一条**抓取直接上前台**的路径，判定用的是
`DISTINCTIVE` 关键词正则（初出店/専門店/ユニーク/コンセプト…）。这正是
`决策记录/0003` 明令不能存在的路径。

而且实际后果比违规更糟：`npm run export-site` 是**从池子完全重建**
`data/events.json` 的，所以这个脚本发布的东西会被下一次导出**静默抹掉**。
十五个地域版一直在抓取、判定、然后丢弃——这就是为什么池子里长期只有个位数的
経済新聞候选。

现在它和其他来源一样只写候选池，自己不做任何判决。`DISTINCTIVE` 正则**删掉了、
没有升级成闸门规则**：判断一家店够不够「ユニーク」是"有不有趣"的判断，
`决策记录/0002` 把这类留给人；闸门只处理主办方或场馆声明的事实。
真正事实性的部分（开店/闭店/迁址）本来就通过 `changeType` 进后台，
由 `lib/object-type.mjs` 映射成 opening / closing / place。

重写后实跑：15/15 版成功，入池 16 条（opening 8 · discovery 6 · closing 2），
全部 pending。`lib/shop-publication-policy.mjs` 现在只剩 `shopWhy` 一个函数。

**CoRich 没有可用的查询参数过滤。** `category_id`/`pref_id` 在 GET 请求上不生效
（实测每个 `category_id` 都返回同样的未过滤总数），只能整页抓下来，
按每条自己的 `.theater .pref` 文本判断是不是东京都。这也意味着**没有按类型
过滤**——演剧、音乐剧、落语、能楽、2.5次元舞台混在一起，这是刻意的：
方案 §3.2「小型文化与亚文化」要的就是这种长尾，不该在抓取阶段就按"像不像
主流剧场"筛掉。

**SCRAP 分两种页面模板，且只接了 3/6 家东京店。** 池袋・吉祥寺共用一套
`ul.list02` 模板（域名 scrapmagazine.com），東京ミステリーサーカス（新宿）
是完全不同的 `article.js_eventsItem` 模板（域名 mysterycircus.jp）。
另外原宿・浅草・渋谷三家店挂在 `realdgame.jp`，那个域名的 `robots.txt`
里 Sitemap 指向一串像是被 SEO 插件污染过的乱码文件名，先不碰——不是技术
做不到，是信号不干净。

**SCRAP 有常驻不设结束日期的游戏，会随时间推移悄悄跌出可见窗口。**
现有的"无结束日期＝单日活动"假设第一次撞上"无结束日期＝长期常驻"，
候选会被正常抓到、正常入池，但 180 天窗口一过就从 `/backstage` 和
`npm run review` 里消失，即使这个游戏其实还能订。这是对象模型本身的
缺口，见 `scripts/sources/scrap.mjs` 里的注释，没有强行打补丁。

**吉本兴业按剧场聚合，不按场次。** 一个喜剧剧场一天三四档，60 天的 feed
就是每馆约 220 行、四馆合计 832 行。按场次入池根本没法判——没有人会为
「ルミネtheよしもと 值不值得去」判 220 次。**剧场是去处，节目是它的排期**，
和中野百老汇同构，只是发生在时间轴而不是楼层上（方案 §4.3）。

为此给管线加了个可选的 `aggregate(events, source)` 钩子：行照常解析，
由来源自己决定"什么算一条候选"。返回空数组表示"没有候选"，不是"抓取失败"。
四条注册各出一条 `place`，卡片写「61日間で218公演。出演：…」。

⚠️ feed 把节目写成「[企画ライブ]ケビンス」「もう中学生／ゲスト：蛙亭」，
不剥掉标签的话卡片会把「[企画ライブ]ケビンス」当成艺人名列出来。

**吉本兴业用的是内部 feed API，不是网页。** 排期页面本身是 JS 异步渲染的，
真正的数据来自 `feed-api.yoshimoto.co.jp/fany/theater/v1`——从官网自己的
`event.js` 里读出来的调用方式，无需鉴权。这台主机自己的 `robots.txt` 返回
的是 API 网关鉴权错误（403），说明它本来就没打算被当成"网页"看待，
无所谓允不允许爬。这条经过 2026-08-28 明确确认后使用，且约定按现有的
"每天一次"节奏跑，不额外加频率——4 个东京剧场每次抓取各一次请求，
±60 天窗口，和官网自己一次页面加载请求的量级相当。

## 场馆催事日历：和其他来源不是一个形状

**東京都立産業貿易センター 台東館 / 浜松町館（`sanbo.mjs`）** 是第一条
**场馆日历型**来源，和其余所有来源的形状不同：别的来源是「某个主办方自己的
活动」，这条是「**任何人订了这个厅之后要办的事**」。

这两个馆是东京小型即売会的物理枢纽——爬虫類、アクアリウム、小動物、鳥、
昆虫、手作り、書道 全在这儿办，主办方大多小到不值得为它单写一个适配器，
而且基本搜不到。读场馆日历一次就能全覆盖。文档第五轮里那条
「爬虫・奇蟲・珍獣フェア!!」就是这么捞出来的，五路关键词搜索都没搜到过。

两个字段让判断变得异常便宜，且都是**场馆自己的登记记录**而非任何人的猜测：

| 字段 | 取值 |
|---|---|
| `区分` | 展示会・見本市 / イベント / **即売会** / 会議・研修・セミナー / 展覧会・発表会 / 試験・審査・競技 / 就活関連 |
| `公開区分` | **公開 / 招待 / 関係者のみ** |

后者映射到 `audience`，由 `lib/gate.mjs` 的 **`rule:not_open_to_public`** 判决
——和 Big Sight 的 `来場対象者` 驱动 `rule:trade_only_admission` 是同一类证据：
场馆记录的「能不能进」，不是「有不有趣」。**没有徽章的行保持 pending**，
因为「没写」不是一种声明，安全的读法是「该有人看一眼」而不是「不开放」。

日历只朝前看：过去的月份返回 0 条，向前约 10 个月。**没有归档**，所以每日
重抓不会丢东西，`sanboUrls()` 走一个滚动的 12 个月窗口。末尾几个空月份是
正常的，不是解析器坏了。

两个实现上的坑：

- **URL 不能带尾斜杠**（`/taito/event?year=…`），站点自己的链接就是这么写的。
- **非公开条目也有 `<a>`，但 href 是 `javascript:void(0)`**。当成链接会产出
  一堆 sourceUrl 字面等于 `javascript:void(0)` 的候选。只认 `/event/<数字>`
  形式的路径，其余回落到月历页。

`robots.txt` 是 `User-agent: * / Disallow:`，全站放行（2026-08-28 确认）。

首轮实测：两馆 12 个月窗口共 **80 条**（台東館 36 · 浜松町館 44），其中即売会 19、展示会・見本市 19、
イベント 25、就活関連 8；`招待` 9 + `関係者のみ` 8 共 17 条被新规则判掉。

**東京ビッグサイト 没有再接一遍。** 它的 HTML 检索接口能回溯到 2009 年
（见 `docs/信息获取管道设计.md` 第五轮补），但那是**已经办完的**展会，
对候选池没有意义；未来的场次现有的开放数据 CSV 已经覆盖，且 CSV 的
`来場対象者` 比 HTML 更规整。那个历史接口的价值是**调研时用来发现垂类名字**，
不是入池，所以没有做成适配器。

## 手动/偶发触发来源（不在每日 cron 里）

某些来源绑定的是现实中周期性举办的展会，不是每天都有新数据——展前几个月
出展者页面是空的，展会结束后目录也不再更新。挂进 `scripts/sources/index.mjs`
的每日 `SOURCES` 只会带来几百次徒劳的重复请求，所以这类来源做成独立脚本，
临近展期手动跑一次。

**東京ハンドメイドマルシェ（`scripts/sources/handmade-marche.mjs` +
`scripts/collect-handmade-marche.mjs`）** 是用户提出的「展会出展者名单」思路
的第一个落地：小众个人创作者店铺普遍靠展会获客，展会自己的出展者目录就是
一份现成的、结构化的店名/品类清单，比逐个找小众店铺的独立官网高效得多——
这个思路不限于古董，任何靠展会获客的小众业态都适用。

结构上：真正的字段（创作者名、品类标签、展位号、出展日、SNS 链接）只在
各自的 `/creators/?exhibitor_id=<id>` 详情页上，列表页只给 `exhibitor_id`。
所以一次完整抓取是「列表页数 + 出展者数」次请求，东京一届约 760 次——
这正是它不能进日常 cron 的原因。

> **⚠️ genre 参数的坑（2026-08-28 修，曾经真的丢了 93% 的数据）**
>
> `/creators/list_creators/?genre=<id>` 看起来是按品类分页，会返回像模像样的
> 约 49 条，所以第一版实现就去遍历品类再取并集。**实际上 `genre` 参数在缺少
> 表单的 `s` 标记时被完全忽略**：每个品类返回的都是同一批 49 条，全部品类的
> 并集还是那 49 条——而东京一届真实有 **722** 个出展者。
>
> 这和 CoRich 的 `category_id` 是同一类坑（见下文「CoRich 没有可用的查询参数
> 过滤」）：**筛选参数被接受、什么都不改变、还返回足够多的行让你以为它生效了。**
>
> 带上 `?s=` 检索才真正执行，并按 20 条分页。所以现在的发现逻辑是走
> `?s=&page=N` 完整翻页、**完全不带品类筛选**——比坏掉的品类循环请求数更少，
> 而且拿得全。翻到空页即结束。采集脚本还会把走下来的条数和页面自报的
> 「全 N 件」对账，不一致就告警——这个 bug 当初就是因为没有对账才藏住的。

这也顺带废掉了原先那份手工维护的品类清单（曾经故意排除 90 公式ブース /
91 PRブース、保留 92 キルト出店エリア）：既然不再按品类发现，就不需要它了。

**同一运营方在全国办 10 场，每个城市一个子域，共用同一套 HTML**
（`handmade-marche.jp` 本身是横滨场，其余是 `tokyo.` `knz.` `kkr.` 等子域），
所以一个解析器覆盖全系列，`--site` 选城市。规模差别很大：东京 700 摊，
**横滨 2,500 摊**，札幌 1,200，名古屋/小倉/金沢 各 1,100。
**默认只跑东京**——跑不跑东京以外的场次是"这个站的地理边界到哪"的产品决定，
必须显式指定，代码不替你做主。

`robots.txt` 明确点名 ClaudeBot 等 AI 爬虫为「意图性允许」（AEO 方针，2026-08-28
确认）——和 fmfm.jp 明确拉黑同一批爬虫正相反。

用法：`node scripts/collect-handmade-marche.mjs --site tokyo --year 2026`，
临近每届展会手动跑。

**Maker Faire Tokyo（`scripts/sources/maker-faire-tokyo.mjs` +
`scripts/collect-maker-faire-tokyo.mjs`）** 是同一个思路的第二个来源，条件
更好：`robots.txt` 是普通的默认设置（只挡 `/wp-admin/`），没找到限制转载的
利用规约页；发现成本也低得多——50 音索引页（`?n=101..114`）14 页就能列出
2026 届全部约 290 个出展者，而且**索引页的分页是真的按索引分片，不像手作市集
那个假的 genre 参数**。每个出展者的展期是全场固定的两天，不像手作市集要按行
解析单独的出展日，字段直接来自 `source.startDate`/`endDate`。

赞助商展位带 `SPONSOR` 标签，但和其他出展者一样有自己的品类标签、简介、
展位号——**明确问过是否要排除**，答复是"都收进来，留给后台判"，
所以抓取阶段不做任何过滤。

用法：`node scripts/collect-maker-faire-tokyo.mjs --start 2026-09-05 --end 2026-09-06`，
临近展期（2026 届为 9 月 5-6 日）手动跑。

**M3（音系・メディアミックス同人即売会，`scripts/sources/m3.mjs` +
`scripts/collect-m3.mjs`）** 是同人音乐即売会，一年两次在東京流通センター，
约 1,700 个社团卖自己录的作品。**接它的理由是它的品类表**——レトロゲーム音楽、
音ゲー、東方project、VOCALOID、ドラマ・トーク（放送劇・声優）、実験映像
是**主办方声明的独立分类**，不是谁猜的标签。这正是方案 §3.2 要的长尾，
而且这些东西在任何场馆日历上都不会出现。

前台是 Next.js SPA，但它读一个**公开无鉴权的 REST API**，比爬渲染后的页面好得多：

| 端点 | 内容 |
|---|---|
| `GET /exhibitions` | 全部届次，`isActive` 标出当前届 |
| `GET /exhibitions/{id}` | 该届的 `eventDate` |
| `GET /circles/{id}` | **约 1,700 个社团一次全量返回**（1.5MB） |
| `GET /companies/{id}` | 企业出展（没有采集——这里要的是个人社团的长尾） |

**两个字段让候选卡片不需要我们编任何理由**，且都是社团自己写的：
`prText`（自我推介全文）与 `keywords`（自填标签）。实测 1,741 条里
**品类和自述 100% 覆盖，97% 带自己的官网或 SNS**。

品类码表（21 个）是从它列表页 SSR 出来的 `<select>` 里抽的——API 只返回
`A14` 这样的裸码，且没有码表端点。**未知码原样透传而不是丢掉**，
这样新增分类会以它自己的样子出现，而不是凭空消失。

`eventDate` 是 `2026-04-24T15:00:00.000Z` 这种形式，**按 UTC 读会少一天**
（15:00Z 正好是 JST 次日零点），必须按 Asia/Tokyo 折算。

### 为什么它是独立脚本而不是日常来源

不是因为成本——一次全跑只要 3 个请求。是因为**届次 id 算不出来**，
必须先查 `/exhibitions`，而注册表的日常来源用的是模块加载时就固定的 URL 列表。
写死 `/circles/2026s` 的后果是：展会过去之后它仍然返回那一届完整的 1,700 行
——响应看着满满当当、不报错、不触发 `empty_parse` 告警、而且再也没有新东西。
这正是第五轮警告过的**季节性来源的静默失效**，所以届次改成运行时解析。

同样的道理还加了一道**过期守卫**：两届之间 API 会一直把上一届标成 active，
这时候直接跑会把约 1,700 条**已经办完、永远不可能发布**的候选灌进本来就在
积压的待判队列（已知问题 #1）。所以解析出的日期早于今天就拒绝执行并说明原因，
要回填旧届次得显式加 `--allow-past`。

三个主机都没有 robots.txt（404），无限制；目录本来就是发布给来场者查阅的。
2026-08-28 确认。

用法：`node scripts/collect-m3.mjs`（自动选当前届）或 `--edition 2026s`。

**文学フリマ東京（`scripts/sources/bunfree.mjs` + `scripts/collect-bunfree.mjs`）**
是文艺自出版即売会，约 3,200 个出店者、東京ビッグサイト、一年两次。
接它的理由是**品类词表**：出店者从主办方的两级分类里自己挑，
`詩歌|現代詩・散文詩`、`小説|妖怪・もののけ`、`評論・研究|建築・都市計画`、
`評論・研究|郷土`——长尾已经被做东西的人自己标好了。

`/c/{届次}/all/50` **一个请求渲染全部出店者**（1.6MB），每行给
ブース / 出店名 / 详情链接 / 品类。届次的日期、场地、正式名都从页面
`<meta name="description">`（形如「「文学フリマ東京42」(2026/5/4、東京ビッグサイト) の
全出店者リストです。」）里读，不用硬编码。各出店者的详情页（紹介文・SNS・販売物）
要再花约 3,200 个请求，**故意不抓**。

实测 42 届：3,237 条全部解析、id 无碰撞、品类 100% 覆盖。

### 三条访问限制，逐一实测（2026-08-28）

同一台机器、同一 IP、同一时刻：

| 客户端 + UA | 结果 |
|---|---|
| `curl` + 项目 UA | **200** |
| `curl` + 空 UA / `curl/8.0` / 裸 `Mozilla/5.0` | 403 |
| **Node `fetch` + 项目 UA** | **403** |

1. **存根式 UA 被拒。** 不需要伪装浏览器，只是不能发空的或库默认的 UA。
2. **境外 IP 被拒，且是站方明文政策。** 利用規約：「不正アクセス防止の観点から、
   日本国外のIPアドレス・匿名プロキシ・匿名VPN (Tor など) 等を経由した通信…
   を自動的に遮断する場合があります」。**所以这条来源不能进 CI**
   ——GitHub Actions 的出口在境外。这是要遵守的，不是要绕的。
3. **Cloudflare 按客户端指纹拦截。** UA、IP、时刻全都一样时 curl 200 / Node 403，
   差别只在 TLS/HTTP 客户端指纹。

第 3 条的处理经过明确确认后定为：**用 `curl` 子进程发请求**
（`scripts/lib/curl-fetch.mjs`，一个 fetch 形状的薄封装）。
边界写在那个文件的注释里，这里重复一遍要点：
**我们仍然发送项目自己的诚实 UA，不伪装浏览器；robots 与站方明文规则全部遵守
（包括不绕境外 IP 限制）。curl 只是另一个正规 HTTP 客户端。
伪造浏览器 TLS 指纹是另一回事，本仓库任何地方都不做。**

robots 允许 `/c/`（只禁 `/anonymous /admin /api /error /payment /legal`），
另外逐条封了一长串具名 SEO/归档爬虫，我们不在其中。
利用規約 §3 反而写明投稿内容可能被转载到其他站点，没有禁止抓取的条款。

### 两道守卫

- **未公开的届次会 302 跳回目录首页**，跟随重定向会把它解析成"空展会"。
  所以请求用 `redirect: manual`，检测到 3xx 就报"该届名单尚未公开"并退出。
  实测 `tokyo43` 正是这个状态。
- **过期届次的名单仍然可访问**，直接抓会把三千多条已经办完、永远不可能发布的
  候选灌进本来就积压的待判队列。日期早于今天就拒绝执行，要回填得显式
  `--allow-past`。与 `collect-m3.mjs` 同一条规矩。

用法：`node scripts/collect-bunfree.mjs --edition tokyo43`，从日本网络跑。

## 展会名单的另一种读法：出展者是店铺，不是事件

这一节记的是一个**取向上的修正**，比任何单条来源都重要。

前面几条展会来源都把展会日期当成候选的日期，于是出展者被建模成**会过期的事件**
——180 天窗口一过就从后台消失。但持久的实体是**店铺/创作者本身**，
展会只是发现它的路径。展会办完之后，那家八王子的化石店照样开着。

对象模型里本来就有这一档：`place`（值得专程去的场所）。走
`changeType: 'discovery'`，`lib/object-type.mjs` 会归到 `place`，不依赖展期。
**缺的从来不是模型，是采集时的取向。**

**但判据必须是"有没有实体地址"，不是"参加过哪个展会"。** 出展者的性质差别很大：

| 展会 | 出展者是什么 | 能否作为 `place` |
|---|---|---|
| 東京ミネラルショー | 有住所的矿物・化石店 | **可以，名单自带地址** |
| 博物ふぇす | 犬養標本店、隕石化石のサイトウ 等 | 多数是店，但要看各自官网 |
| とんぶり市 | 个人繁殖者 | 少数有店面 |
| 手作市集 / Design Festa / 文学フリマ | 个人创作者 | 多数只在网上卖，不是可去处 |

证据由便宜到贵：①名单自带住所 → ②出展者官网上有 `店舗情報/アクセス/営業時間`
→ ③什么都没有，那就只是个创作者，留在池子里但不当 `place`。
**不要因为这条路在矿物展上跑通，就把它套到手作市集上。**

顺带说明：`collect-m3.mjs` 与 `collect-bunfree.mjs` 的过期守卫**依然是对的**。
它们挡的是"把办完的展会当**事件**入池"，和这里"换个对象类型采集同一份名单"
是并行的两条路径，不冲突。

### 東京ミネラルショー（`tokyo-mineral-show.mjs` + `collect-mineral-shops.mjs`）

这条路径的第一个落地，也是全部调研里最干净的例证：**主办方在每个出展者的
摊位号旁边直接印了邮编、住所和电话**，不需要任何推断。

名单在 WordPress 页面里，10 个 slug（`exhibitor` 是あ行，其余 `list_ka`…
`list_ya` 加两个海外页），走 `wp-json/wp/v2/pages?slug=` 取内容最省事。
每个出展者是**两行**：数据行（社名/会場/エリア/ブースNo）+ 单格的住所电话行。

实测：417 行 → 307 行有地址 → **112 家在东京都**，全部作为 `place` 入池。

**故意不采集电话和邮箱。** 其中若干是主办方特意做了混淆的私人邮箱
（`kazariya.akitsu3☆gmail.com` 把 `@` 写成 `☆`）——绕过它就等于破坏一个
替出展者做的保护。地址才是让店能被找到的东西，只留地址。测试里有一条断言
守着这个（任何候选的 place/why/title 里都不许出现 `@ ☆ ★ ＠`）。

另一个坑：地址里的「番地-号-室号」（`5-26-14-104`）长得和电话号码一样，
写清洗正则时**先剥邮编、再剥带 TEL/FAX 或以 0 开头的号码**，不能见到
数字-数字-数字就删。这条也有回归测试。

**あ行页目前是「現在制作中」，整张表被 HTML 注释包着**，所以解析出 0 行——
这是正常状态不是解析器坏了，脚本会打一行 warning 而不是报错。也因此
**当前拿到的是上一届（11/17 时点）的名单**，这恰恰是本节的重点：上一届的
出展者今天依然是店。

只保留 `東京都`（`--prefecture` 可改）。山梨・神奈川・大阪的矿物店是真店，
但不是东京探索队列的去处，和 corich.mjs 的过滤同一个道理。

**已知缺口（和 scrap.mjs 记的是同一个）**：池子没有「常驻、无已知结束日」
的概念，horizon 过滤把「无 endDate」读成「单日活动」。所以这里给了一个
一年后的 endDate 让店铺留在可见窗口内，等下次运行刷新。
**那是给缺失概念打的补丁，不是对这家店的断言。**

### 这条路能走多远：实测了五个展会，只有一个成立

「出展者是店铺」的想法对，但**能不能落地完全取决于名单页上有没有印地址**，
而这件事比想象中罕见得多。逐个实测（2026-08-28）：

| 展会 | 出展者性质 | 名单页有地址？ | 结论 |
|---|---|---|---|
| **東京ミネラルショー** | 矿物・化石**業者** | **有**（邮编+住所+电话） | ✅ 已实现，112 家入池 |
| 博物ふぇすてぃばる！ | 標本・骨格**作家** | 无 | ❌ |
| アクアリウムバス | 熱帯魚店・繁殖者 | 无 | ❌ |
| ミネラル・ザ・ワールド | 矿物**業者** | **无** | ❌ |
| ミネラルフェスタ横浜 | 矿物業者 | 无 | ❌ |
| 東京レプタイルズワールド | 爬虫類**業者** | 无 | ❌ |
| **モノマチ**（オープンファクトリー） | 台東区の町工場 | **有**（125/127 带住所+经纬度） | ✅ 已实现 |

**我原本以为的规律「業者展有地址、作家展没有」是错的。** 那三个矿物/爬虫類展
都是不折不扣的業者展，一样不印地址。真实情况是：**印不印住所是每个主办方各自
的选择，和展会性质无关**，只能一个个实测。

后来接的 モノマチ 又从另一个方向印证了这点：它是オープンファクトリー（町工場
开放日）不是業者展，却把住所印得最全（还带经纬度）。**判据自始至终只有一条
——名单页上有没有地址。** 所以判断只能一个个实测，
不能从展会性质推断——这和第五轮那条「有没有名单页必须逐个实测」是同一个教训，
只是下沉了一层。

#### 博物ふぇす 的数据说明了作家展为什么走不通

679 条正文全文里：`営業時間` 0 次、`住所` 0 次、`アクセス` 0 次、`常設` 0 次、
`実店舗` 2 次、`店舗` 8 次。外链构成是 X 314 + Instagram 294 + minne/creema
等网店 33——**压倒性地是线上创作者**。アクアリウムバス 的 144 个外链同理：
40 个 x.com、40 个 instagram，其余大量是 ocnk / stores.jp / base.shop /
booth.pm 这类网店平台，实体店是少数且不少在东京之外。

#### 那条更贵的路：去出展者自己的网站上找地址

理论上可以对每个出展者的官网抓一次，找 `店舗情報/アクセス/営業時間`。
**没有做**，原因是收益比太差：大部分外链是 SNS 和网店平台（根本没有地址页），
要为少数实体店去抓几百个第三方站点，还要处理各式各样的页面结构，
噪声远大于产出。如果哪天要做，正确的起点是**先筛出带独立域名的外链**
（不是 x.com / instagram / ocnk / stores.jp 这些），那才是可能有实体店的子集。

#### 已抓来源里还有多少「持续存在的店铺」

盘点当前池子里来自展会的候选：手作市集 708（个人创作者）、
Maker Faire 287（个人 maker 与企业展位）、東京ミネラルショー 112（**店铺**）。
**结论是：已经扒过的展会里，能变成 `place` 的就是矿物展这 112 家**，
其余的性质就是创作者不是去处。这不是可惜，是把话说准了——
把线上创作者当成「值得专程去的场所」塞进探索队列，才是真的坏事。

### オープンファクトリー：第二条「出展者是店铺」的来源

**モノマチ（`monomachi.mjs` + `collect-monomachi.mjs`）** —— 台東区
（御徒町〜蔵前〜浅草橋）一年一次、几十家町工場同时开放的活动。
**它清过了「名单带实体地址」这道门槛**，而且比矿物展还好：127 条里
**125 条带完整台東区住所，还带经纬度**。

前台是 React SPA，但数据是一个无鉴权的裸 JSON：
`https://{年}.monomachi.com/monomachi_data_{年}.json`（约 1.1MB）。
`shops` 是店铺目录，`all_events` 是那个周末的节目单——**后者是真正绑日期的，
没有采集**，把它变成 place 等于宣称那家工房天天办工作坊，是假话。

品类就是要找的长尾：傘屋・革小物・草木染め・ボタン専門店・ガーゼ専門店・
仏壇仏具・**銭湯**・ヘアケア化粧品・アンティーク。

**故意丢掉电话和邮箱。** 载荷里有 `phone` 列，自由文本里散着 92 个工房的
邮箱地址。和矿物展同一个判断：住所才是让工房能被找到的东西，
把小店的直接联系方式汇编起来不是这个项目该做的事。有测试守着。

实跑：127 行 → **125 家入池为 `place`**，`ongoing: true`（工房没有结束日）。

### 负面结论（别再花时间）

- **DNS 不存在**：`oota-openfactory.jp`、`o-monozukuri.com`、`a-round.info`、
  `ofs.jp`、`kougei-expo.jp`、`tokyo-teshigoto.tokyo`（正确域名是
  `tokyoteshigoto.tokyo`）。
- **浅草エーラウンド**（奥浅草・皮革）域名已丢，按停办处理。
- **陶器市的出店者一覧只有名字没有住所**——笠間の陶炎祭（200+ 窯元，
  出店位置只在"作成中"的 PDF 地图里）、益子陶器市（窯元名录只有名称+电话，
  且站点 HTTPS 握手失败、页面是 Shift_JIS）。这类**只能当一个事件收**
  （一个会场一个住所），拆不成一堆场所。
- **全国伝統産業会館一覧**（`kyokai.kougeihin.jp/hall/`）只有名称+県名，无住所。
- **かつしかライブファクトリー**、**燕三条 工場の祭典**（157 家）、
  **RENEW**（约 120 社）都是 SPA，数据要逆向
  `api.studiodesignapp.com/data_proxy_api` 或 `admin-ajax.php`——**未坐实**。
  RENEW 的筛选轴设计（コンテンツ×開催日×ジャンル×エリア×予約要否）值得照抄。

**おおたオープンファクトリー（`oota-open-factory.mjs` +
`collect-oota-open-factory.mjs`）** —— 大田区是东京町工場密度最高的地方，
一年一次约三十家开门。同 モノマチ 一样按 `place` 收：活动只有一天，工厂全年都在。

两段式，因为两半数据分开放：REST `wp-json/wp/v2/posts?per_page=100` 枚举工场
（一次请求，无需解析 HTML），详情页才有住所和内容。**REST 的 `content.rendered`
只有一句标语，所以第二段不是可选的**，没有能直接拿到住所的捷径。

三个把天真解析打回来的地方，都有回归测试：

1. **住所不带都道府県**——「大田区下丸子4-19-20」。其他店铺来源用的
   `startsWith('東京都')` 过滤在这里会把**每一行**都拒掉。
2. **一家工场可能列多个住所**，带圈号：
   「① 大田区下丸子2-11-1（多摩川工場）※工場見学ツアー住所 ② …（洗濯資料館）」。
   圈号让整格解析失败，白洋舍 因此被当成"没有住所"丢掉——**它其实公布了两个**。
   现在取第一个（活动带人去的那个），切掉后续条目和 ※ 脚注。
3. **少数行给值加了标签**：「【開催場所】東京都大田区…」。不剥掉的话，补前缀那步
   会产出 `東京都【開催場所】東京都大田区…`。

页面没有 `<h1>`，工场名要从 `<title>` 的 ` | ` 之前取；`.l-title` 里是
名字+所在エリア。住所那格的文字包在 Google Maps 链接里，坐标在 href 的
query 上——**要读 `<span>` 的文字，不是 href**。

电话与传真同样故意不采。

**2026 届（11/28）的站点已经在了，但工场名单还是空的。** 采集脚本会认出
"站点 200 但列出 0 家"这种预告状态并回退到上一届，而不是当成成功——
这正是 0004 那条教训：产出为空却一切正常，是最难发现的失败。

用法：`node scripts/collect-oota-open-factory.mjs`（自动找最新有名单的一届）。

**おうめオープンファクトリー（`oume-open-factory.mjs` +
`collect-oume-open-factory.mjs`）** —— 青梅市，三条オープンファクトリー来源里
**成本最低的一个：整份名单就是一个页面**，一次请求拿 35 家。每家是一张

小澤酒造、明治7年创业的原島製畳、銅板造形工房 Studio fu-mine、
巻きチョコ 的プラム。

三个解析要点：

- **住所、電話、官网挤在同一个 `<p>` 里用 `<br>` 分行**，必须按行切。
  当成一个字符串读，住所会变成「青梅市沢井2-770 0428-78-8215 https://…」。
- 住所同样**不带都道府県**（青梅市…），和大田区一样要补。

- 住所里的括号补充（「青梅市梅郷6-1438-1(作業場)」）**保留**——
  它告诉来客该去这家公司的哪栋楼。

电话同样故意不采。这个页面全年都在、改届时会被清空，所以**解析出 0 家时
脚本报错退出而不是当成成功**（0004）。

用法：`node scripts/collect-oume-open-factory.mjs`。

### 「一个地址一个候选」回头改掉了两条已有来源

中野百老汇立下这条规矩之后，回头看池子发现同样的错误早就犯过两次：

| 来源 | 原本 | 现在 |
|---|---|---|
| 東京ハンドメイドマルシェ2026 | **708 条**（每个出展者一条） | **1 条** |
| Maker Faire Tokyo 2026 | **287 条** | **1 条** |

两个都是**一个会场、一到两天**——对"这周末去哪"只有一个答案。
它们和矿物展的关键差别是：**矿物商有自己的住所，展会结束照样开门；
这些创作者没有公开地址，只在那两天、那个会场存在。**
所以矿物展拆成 112 个 `place` 是对的，这两个拆开是错的。

名单同样变成卡片：
「出展者287組。エレクトロニクス105・ロボティクス73・Young Makers54…」
——这正是判断值不值得跑一趟所需要的信息。出展者名字进了分类器的文本，
所以搜某个创作者依然能找到这场展会。

两条实现细节：
- 手作市集的展期**取全部出展者出展日的最小值与最大值**，
  而不是碰巧第一个被解析到的那天，否则两天的展会会变成一天。
- 聚合函数拿不到任何出展者时返回 `null`，采集脚本据此报错退出——
  空产出不能当成成功（0004）。

### 第三种形态：一栋楼就是一个去处

前两种是「展会名单 → 店铺」和「展会名单 → 事件」。
**中野ブロードウェイ（`nakano-broadway.mjs` + `collect-nakano-broadway.mjs`）
是第三种，而它教了一条比来源本身更重要的规矩。**

第一版把 207 家租户各自入池。**粒度错了**：
**决定"去哪"的时候，这 207 家是同一个去处**——去一趟中野百老汇就全逛完了。
207 行等于对"这周末去哪"给出 207 个几乎一样的答案，既淹后台，
也正面违反方案 §7.1 对探索队列"一轮内类型多样"的要求。

改之前实测：池子里 524 个 `place` 折叠后只有 **309 个不同街区地址**，
其中 207 的差额全部来自这一栋楼，**其余任何地址上最多只有 3 个候选**。

> **由此确立：一个地址，一个候选。**
> 散在一个区里的店（モノマチ 的 125 家工房各有各的地址）仍然各算各的，
> 因为那确实是不同的行程。

名单没有被丢掉——**它变成了卡片本身**。让这栋楼值得跑一趟的正是
「専門店207軒が6フロアに密集。サブカルチャー85・ファッション46・飲食29」，
这是关于整栋楼的事实。租户名也进了分类器的文本，所以搜「まんだらけ」
依然找得到这栋楼。

`scripts/check-granularity.mjs` 是配套的诊断（不是闸门）：报告同一街区地址上
挤了多少候选。几家小店共用一栋小楼是正常的，只有人能判断某一簇到底是一趟
还是几趟——它存在是为了让下一个来源没法再悄悄把池子灌满。

两个解析要点：

- **楼层来自分类法而不是正文。** 大楼把每家店归两次：カテゴリ別店舗情報
  与 フロア別店舗情報（含 地下1階 与 プチパリ）。正文提到楼层的只有 208 条里的 6 条。
  分类 id 从实时 taxonomy 读、没硬编码——一个 WordPress 分类 id 只是某次安装的实现细节。
- **不是每条 post 都是店。** NEWS&TOPICS 和店铺混在同一个 `posts` 集合里，
  **没有楼层分类的就不是租户**——楼层既是有用字段也是可靠过滤器。

同形态可复制的对象：秋葉原ラジオ会館、まんだらけ系、吉祥寺ハモニカ横丁、
新宿ゴールデン街、立石——**每栋楼一个候选**。

### 运动设施：从开放数据里捞「哪里能射弓道」

**区市町村のスポーツ施設（`sports-facilities.mjs` + `collect-sports-facilities.mjs`）**
填的是方案 §3.2 里一直最空的「新运动与参与式消遣」，而且是从唯一走得通的角度。

**「几号有弓道教室」走不通，「哪里能射弓道」走得通。** 课程排期锁在各区
会员制预约系统后面（见下方负面结论），但**设施本身是各区自己发布的开放数据**。

推奨データセット格式给每个竞技项目**单开一列**，由区里填 `有`/`無`。
所以「这个体育馆能射弓道」是**设施运营方声明的事实**，不是从名字里猜的关键词
——和 Big Sight 的 `来場対象者` 同一类证据，符合 0002 对规则证据的要求。
全部数据集是 **CC BY**，明确允许再利用，署名即可。发现走東京都 CKAN 目录。

实测：62 个可读数据集、1,071 个设施，**139 个提供至少一项小众项目**（入池去重后 125）：

```
弓道35 / なぎなた28 / 空手道19 / フェンシング15 / アーチェリー6
柔道4 / レスリング3 / 銃剣道3 / カヌー2 / 剣道2 / 相撲2 / ボクシング2
アイスホッケー1 / 山岳・スポーツクライミング1 / スケート1 / ホッケー1
```

> **判据改过一次，第一版是错的（2026-08-30）。**
> 第一版留「有小众竞技项目」的设施——弓道・なぎなた・フェンシング。
> **人工判决 11 条里排除了 9 条**，包括一栋干脆叫「弓道場」的建筑。
> 原因值得记下来：**区立体育馆有弓道場，不等于它是个去处**。要在那儿射箭
> 得先入会、先预约、自己带装备——**房间存在，出行不存在**。
>
> 活下来的是另一种性质：**能不能直接去玩**。泳池、滑板场、独木舟场是；
> 体育馆里的一个武道室不是。所以现在按**设施名**筛（`LEISURE_FACILITIES`），
> 因为"能直接去玩"这件事写在名字里；竞技项目那些列只用来**描述**留下来的设施。
>
> 另外排除两类：**学校设施**（「五本木小学校屋内プール」「品川学園温水プール」
> 只对区民限时开放，不是周末临时起意能去的地方）和**已停用的**
> （「あきる野市民プール（屋外）（令和8年まで閉場）」）。
>
> ⚠️ 停用只看**名字**。开放时间栏里满是「第２・４火曜日休館日」这种常规休息日，
> 把它读成"停止服务"会误杀正常运营的泳池。区里把闭馆写进设施名，才是真的。
>
> **已知缺口：数据里没有"是否对外营业"字段**，只有开放曜日与时间。
> 排除学校设施是个代理判据，不是保证。
>
> 1,042 个设施里约 57 个通过（原为 139），**而且是完全不同的 57 个**。

两个踩到的坑，都有测试：

- **列的取值是 `有`/`無`，不是空/非空。** 把"有这一列"当成"提供这项运动"，
  会让每个设施都提供所有运动——第一次实测十二个项目**各命中 169 次**，
  这个整齐得可疑的数字才把 bug 暴露出来。
- **目录里有失效的 CSV 链接**（65 个里 3 个 404）。死链要跳过该区，不能中断整轮。

用法：`node scripts/collect-sports-facilities.mjs`，约 65 次请求。

### 剧本杀：一篇文章就是一份店铺目录

**マダミスマニア（`mdms-mania.mjs` + `collect-mdms-mania.mjs`）** 补上了
`docs/信息获取管道设计.md` 第二轮标记「能做但未接」的剧本杀品类。
`robots.txt` 只挡 `/wp-admin/`，站点没有单独的利用规约页面。

`/store/tokyo/` 不是结构化列表，是一整篇手写文章：每家店是一个 `<h3>`
（或者，连锁店的其他分店，一个 accordion 里的 `<h4>`），紧跟着一张
`<figure class="wp-block-table">`，行按 住所/アクセス/電話番号/営業時間/公式サイト
取名。**同一个 accordion 里经常混着大阪、名古屋的分店**，所以按每家店自己的
「住所」是否以「東京都」开头筛，而不是按它出现在文章哪个小节。

这些是 `place`，不是按日期排的活动——店不会"开始"或"结束"——所以走
中野ブロードウェイ那条路：`startDate` 取抓取当天，`ongoing: true` 标记
不受"已结束"过滤（仍受 180 天窗口约束）。实测 21 家东京分店，去重后 17 个
不同地址（同一家分店有时在文章里被提到两次，标题和地址完全相同，
天然合并成一条）。

不是每日抓：这是一篇文章不是事件流，门店变化按月计不按天计。

## 已知的坑

**早稲田大学的 robots.txt 取不到（已解决，但留个说明）。**
`https://www.waseda.jp/robots.txt` 返回的是 Cloudflare 的 403 挑战页，换任何
User-Agent 都一样（含空 UA 与浏览器 UA），而活动列表页 `/top/event/list` 对我们的
UA 正常返回 200。所以这个站**没有可取回的 robots.txt**，不是它禁止了我们。

此前管线按"非 2xx 即拒抓"处理，把这个来源整个丢掉了。现在按 RFC 9309 §2.3.1 办：
4xx 表示 robots.txt 不可用、可以访问；429 与 5xx 表示答案未知、不抓。
但**非 404 的 4xx 会在注册表里记 `robots_unavailable` 警告**——放行是明面上的，
不是悄悄的。

如果哪天早稲田的 robots.txt 变得可读且写了 Disallow，管线会自动改回拒抓，
不需要改代码。

**Big Sight 的公开性判定仍然只看一个字段。** `isPubliclyAccessible()` 检查
`audience` 是否含「一般」。换成开放数据后这个字段变成了主办方的权威声明，
比原来的正则猜测可靠得多，但方案 §5.2 的五条保留条件（能否合法报名、
是否要求虚构身份、现场有无实体展示等）仍然一条都没实现。

**`audience` 字段有两套语义。** Big Sight 用它表示「谁可以来」，
而 `utokyo-events.mjs` 用它装「オンライン」「本郷地区」这类地点/形式。
目前 `isPubliclyAccessible()` 只作用于 Big Sight 所以没有实际冲突，
但这是个契约隐患。

**藝大三个馆共用 `source` 字段。** 三条来源同名，前台无法区分，只能靠 `place`。
注册表里靠 `name::url` 组成的 id 区分，所以健康监测不会把它们混在一起。

## 加一个来源要做的事

1. 先看 `robots.txt` 与使用条款。
2. 在 `scripts/sources/` 建 `<来源>.mjs`，导出 `parse<来源>(html, source)` 和 URL 常量；
   用 `createEventCandidate()` 造记录。
3. 同目录建 `<来源>.test.mjs`，**用内联 HTML 夹具**，不要打网络。
4. 注册进 `scripts/sources/index.mjs`，**填对 `accessMethod`**
   （`html` 用 `parse(html, source)`；`csv`/`json` 用 `map(record, source, index)`，
   取数与编码嗅探由管线负责），并填全方案 §3.3 的字段：`sourceFamily`、
   `trustTier`、`accessMethod`、`crawlFrequency`、`expectedUpdateWindowDays`、
   `robotsAndTermsCheckedAt`、`parserVersion`、`ownerOrContact`。
   **改解析器时同步改 `parserVersion`**——它是重写之后用来定位"该复查哪些来源"的东西。
5. 跑一次 `npm run update-events`，再跑 `npm run check-sources` 确认没有告警，
   把原始条数补进上面的表。
6. **不要新建 `index-v2.mjs`。** 见 `决策记录/0001-收敛版本树.md`。
