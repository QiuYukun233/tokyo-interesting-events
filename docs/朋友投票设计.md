# 朋友投票 v1 设计

2026-10-12 定。方案 §8.2「活动 → 朋友」的最小切片，也是阶段 3/4 的第一步：
验证「发现 → 成行」这条核心命题，**不建账号、不建群组**。

## 1. 流程

```
想去清单的一项 ──「问朋友」──▶ 生成分享链接 /i/<code>（每项一条，重复点复用）
                                   │ 发到 LINE / 微信群
                                   ▼
朋友打开（无需口令）→ 填昵称 → 想去 / 可以 / 不想去
                                   │ 投完才揭晓
                                   ▼
「你们都想去！」/「可以一起去」/「这次不成」+ 其他人的回复
                                   │
想去清单上同一项显示所有回复（小王 想去 · 小李 可以）
```

## 2. 数据（Turso，云端独有，与 votes 同级）

- `invites(code PK, candidateId UNIQUE, snapshot JSON, createdAt)`
  - `code`：128 位随机 base64url，是这条链接的**唯一凭证**（能力链接）。
  - `snapshot`：建链接时冻结候选的展示字段。push-cloud 会删掉被硬排除的候选，
    链接不能因此变成死链。
- `invite_replies(inviteCode, responderId, name, vote, respondedAt, PK(inviteCode, responderId))`
  - `responderId`：朋友浏览器里 localStorage 生成的随机 id，改票是覆盖不是追加。
  - 每条链接最多 30 条回复，昵称最长 20 字。

**朋友的票不进 `votes`。** `votes` 是「我」的品味层（探索队列设计 §2），
朋友的回复是社交信号，混进去会污染 tag 权重。

## 3. 揭晓规则

- 朋友投票前，`GET /api/invites/<code>` **只返回候选与回复人数**，不返回任何人的票——
  隐藏在服务端执行，不是前端藏（方案 §7.3：减少从众）。
- 投完后返回：发起人（我）当前的票 + 所有回复。
- 匹配标签（`lib/invite.mjs` 纯函数，沿用方案 §7.3 的分级）：
  - 双方想去 → **都想去**
  - 一方想去、一方可以 → **可以一起去**
  - 都是「可以」→ **都觉得可以**（谁都不兴奋，不催成行）
  - 任一方不想去 → **这次不成**

## 4. 鉴权

- 建链接、看想去清单：照旧要 `QUEUE_TOKEN`。
- `/i/<code>` 页与其两个 API：**不要口令**，凭 code 访问且只能看到这一项。
  不暴露候选池、队列、其他链接。

## 5. 明确不做（v1）

- 选日期 / 计划页（方案 §8.1 第 6 步）——先看朋友是否真的会回；
- 通知（朋友回复后推送）——先在想去清单里看；
- 朋友账号、朋友自己的队列、相似替代项（§8.2 第 7 步）。
