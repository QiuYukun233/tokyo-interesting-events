# 东京有趣信息雷达与朋友探索队列方案

**版本：** 0.1  
**日期：** 2026-08-27

## 1. 产品定义

本产品不是活动搜索引擎，也不是约会软件的换皮。它是现实世界版的 Steam 探索队列：从大量候选中持续生成一个有限、解释充分、值得逐个判断的东京体验队列，并利用朋友之间的共同兴趣把“发现”推进到“成行”。

Steam 的 Discovery Queue 会把推荐、新内容和热门内容混合成有限队列，允许用户加入愿望单、关注或忽略，并每日刷新；Steam 也明确指出，新内容存在冷启动，因此探索队列与行为推荐互为补充而非相互替代。([Steam Discovery Update](https://store.steampowered.com/about/newstore?l=english)，[Steam Labs 说明](https://store.steampowered.com/news/posts/?enddate=1568741223&feed=steam_blog))

我们对应的核心动作是：

- **想去：** 类似愿望单，表达未来真实意愿；
- **可以：** 不是第一选择，但愿意和朋友去；
- **不想去：** 只对当前人或当前群组生效；
- **关注：** 关注场馆、系列活动、店铺或下一期；
- **为什么不想去：** 太贵、太远、没空、不感兴趣、无法入场等，用于区分品味与现实限制。

产品同时服务两条路径：

### 路径 A：先有朋友，再找去处

> “我们周六想出去，但不知道去哪。”

建组 → 汇总时间、预算和硬限制 → 生成群组探索队列 → 成员独立判断 → 揭晓共同兴趣 → 选择日期与预约。

### 路径 B：先有去处，再找朋友

> “我想去这个机器人展，但不知道朋友里谁也感兴趣。”

用户标记想去 → 选择是否向朋友可见 → 系统发现已有兴趣重合或发送轻量询问 → 围绕该活动临时建组 → 确认时间与成行。

两条路径最终汇入同一个“计划对象”，而不是停留在收藏或 Match 动画。

## 2. 为什么内容引擎必须先于社交功能

探索队列的成立依赖三个条件：

1. 候选池足够广，能覆盖用户原本不会主动搜索的内容；
2. 显然无关、无法参加和纯职业导向内容已被排除；
3. 队列中的每一项至少“足够好”或“足够独特”。

因此，爬虫的任务是发现候选，不是直接发布。完整链路为：

`来源监测 → 候选抽取 → 实体归一化 → 去重 → 硬排除 → 入场核实 → 内容补全 → 兴趣评分 → 编辑审核 → 探索队列`

## 3. 广泛信息雷达

### 3.1 来源分层

| 层级 | 来源 | 用途 | 可信度处理 |
|---|---|---|---|
| S0 | 场馆、大学、博物馆、主办方和店铺官网 | 日期、地点、入场、闭店等关键事实 | 可作为事实主来源 |
| S1 | 官方 RSS、公开 API、结构化日历、新闻稿 | 批量发现和状态更新 | 自动抽取后抽样检查 |
| S2 | 可靠垂直媒体和区级本地媒体 | 发现官网之外的背景、开闭店和小型活动 | 关键事实回查 S0 |
| S3 | 店铺社交账号、通讯、海报和社区账号 | 发现碎片化、短提前期内容 | 必须保留原始证据并人工核实 |
| S4 | 用户、校园侦察员和行业人士投稿 | 发现尚未公开传播的线索 | 只进入待核实池，不直接发布 |

### 3.2 首批来源家族

#### 大型展馆与公开展会

- 东京 Big Sight、Ariake GYM-EX；
- 幕张 Messe；
- 东京国际论坛；
- Sunshine City 展示厅；
- 东京流通中心、产业贸易中心；
- 科学未来馆、产业技术研究机构等公开展会场地。

Big Sight 是典型高价值源。其官方日历同时提供日期、入场类型、费用、场馆和主办方 URL，当前日文列表可返回 179 个结果；官方称场馆每年约举办 300 个活动。日历里既有应排除的后台 DX、就业活动，也有国际铁路模型大会、业余无线电展、Maker Faire 等明显适合普通人探索的内容。([官方日历](https://www.bigsight.jp/visitor/event/)，[场馆介绍](https://www.bigsight.jp/english/))

#### 艺术、设计与特殊空间

- 国公立与私立博物馆的展览、夜间开放和后台参观；
- 画廊、艺术大学、驻留机构和设计中心；
- 建筑公开、仓库开放、工作室开放；
- Tokyo Art Beat 等垂直媒体作为发现与补充源。

#### 大学与研究机构

- 东京及周边大学的新闻、活动、一般开放和校园祭页面；
- 独立研究所、实验室、大学博物馆、植物园、农场和观测设施；
- 公开讲座只在内容或场所足够独特时保留，招生说明会默认排除。

#### 新运动与参与式消遣

- 新兴运动场馆、协会、教练社群、体验预约平台；
- 模拟飞行、机器人操控、无人机、击剑、冰壶、城市定向、洞穴或地下设施参观；
- Maker 社群、工作坊、公开制作与短期课程。

#### 店铺生命周期

- 开店闭店媒体、区级本地媒体和商业设施公告用于发现；
- 店铺官网或正式社交账号用于确认；
- 收录新店、搬迁、正式宣布闭店、长期休止和编辑新发现的老店；
- “快倒闭”不得由模型推测经营情况，只能依据明确公告。

#### 小型文化与亚文化

- 独立书店、爵士喫茶、唱片店、小剧场、live house、澡堂、模型店；
- 社区节庆、定期市场、同人活动、收藏与手艺社群；
- 以主办方通讯和公开账号为主要更新信号。

### 3.3 来源注册表

每个来源必须进入 `source_registry`，记录：

```text
source_id
name
source_family
base_url
access_method: api | rss | html | pdf | newsletter | manual
crawl_frequency
expected_update_window
robots_and_terms_checked_at
parser_version
last_success_at
last_item_count
failure_streak
trust_tier
owner_or_contact
```

系统监测“突然抓不到内容”“条数异常下降”“页面结构变化”和“来源长时间不更新”，避免爬虫静默失效。

## 4. 候选抽取与归一化

### 4.1 统一对象模型

“去处”不只是一场 event。统一模型至少支持：

- `event`：有明确时间的单次或周期事件；
- `exhibition`：有展期，可多次到访；
- `place`：持续营业但值得专程去的场所；
- `opening`：新开或重新开放；
- `closing`：正式确认即将消失；
- `activity`：可预约或周期体验；
- `open_facility`：大学、研究所、工厂或建筑的特别开放。

基础字段：

```text
item_id, canonical_name, object_type
start_at, end_at, recurrence_rule
venue_id, organizer_id, location
public_access, registration_required, audience_restrictions
price_min, price_max, language_support
source_urls[], source_evidence[]
why_now, quality_score, uniqueness_score
experience_tags[], friction_tags[]
verified_at, expires_at
```

### 4.2 去重与实体识别

同一展会可能同时出现在场馆日历、主办方官网、Peatix、新闻稿和媒体文章中。不能按 URL 去重，应使用：

- 名称标准化与别名；
- 主办方；
- 场馆；
- 日期重叠；
- 官方 URL；
- 语义相似度。

合并后保留所有来源证据，以官方源负责时间和入场，媒体源负责背景，用户反馈负责实际体验。

### 4.3 候选的单位是「一趟出行」，不是「一个实体」

**（2026-08-29 补。这条是实现中野百老汇来源时撞出来的，不是设计时想到的。）**

4.2 处理的是"同一件事出现在多个来源"。还有一个方向相反、更容易忽略的问题：
**多个真实存在的不同实体，对用户来说是同一趟出行。**

第一次接中野百老汇时，把楼里 207 家租户各自入池——它们确实是 207 家不同的店，
去重逻辑上没有任何问题。但用户一句话点破：

> 这几个地点里所有的店铺对约会来说其实是同一个地方，一次就能覆盖到。

对"这周末去哪"这个问题，207 家店只有一个答案。207 行候选既淹没后台，
也正面违反 §7.1 对一轮队列内类型多样的要求——队列会被同一栋楼填满。

实测印证：当时池子里 524 个 `place` 折叠到街区地址后只剩 309 个，
**207 的差额全部来自那一栋楼**，其余任何地址上最多 3 个候选。

**已落地的规矩：一个地址，一个候选。** 中野百老汇现在是一条候选，
租户名单变成卡片内容（「専門店207軒が6フロアに密集。サブカルチャー85…」）。
诊断脚本 `scripts/check-granularity.mjs` 报告同址候选数，是报告不是闸门。

**尚未解决的部分（留给探索队列开工时处理）：**

"同一个地址"只是这个问题最干净的那一刀。真实的边界是模糊的，
而且**只能靠产品判断，不能靠技术判断**：

| 情况 | 是几趟？ |
|---|---|
| 一栋楼里的 207 家店 | **1 趟**（已按此处理） |
| 矿物展带出的 112 家矿物店，散在东京各区 | 112 趟，各是各的 |
| モノマチ 的 125 家工房，集中在蔵前〜御徒町一带 | 地址各异，但「去蔵前逛一天」可能是 1 趟 |
| 大田区 29 家町工場，且开放日只有那一天 | 那一天大概是 1 趟 |

后两行现在**没有**做任何合并，因为"多近算一趟""同一天的多个点算不算一趟"
是产品决定。记在这里是因为：**做探索队列时这个问题一定会重新浮上来，
到时候可能需要在"地点"之上再有一个"行程"层**——一轮队列里放的应该是
12–20 个*行程*，不是 12–20 个*地点*。

在那之前，新增来源时的自检问题是：
**"如果两条候选都被放行，用户会因此多出门一次吗？"** 答案是否，就该合并。

## 5. 硬排除规则

硬排除解决“这根本不是我们关心的事”，不参与兴趣评分。

### 5.1 默认排除

- 就活、招聘、合同企业说明会、人才面试与校招；
- 招生、升学和普通学校说明会；
- 纯销售、加盟、投资、保险、房地产获客活动；
- 普通企业后台、HR、会计、合规和 SaaS 推介会；
- 仅限持证专业人士、采购负责人或受邀客户且无法合法进入；
- 没有线下体验的普通 webinar；
- 常规商场折扣、积分活动和连锁店普通开业；
- 无法确认日期、地点、入场资格或主办方的内容；
- 已结束、取消、满员且无候补价值的内容。

高置信关键词只是触发器，不是唯一依据：

```text
就活, 採用, 合同説明会, 企業説明会, 転職, 求人,
recruiting, career fair, hiring, franchise, investor seminar
```

### 5.2 不能一刀切的“商谈展”

`Trade / 商談` 不是自动排除条件。工业、机器人、模型、交通、食品设备和新材料展可能拥有很强的普通人探索价值。保留必须同时满足：

1. 普通人可以合法报名或购买入场；
2. 不要求虚构公司、职位或采购身份；
3. 现场有大量实体展示、演示、试用或可理解的视觉内容；
4. 即使没有业务需求，也能说出至少一个具体值得看的东西；
5. 主办方没有明确禁止一般参观。

因此“宠物机器人展”可能高分，“后台人事系统采购会”直接排除。

## 6. 兴趣与编辑评分

通过硬门槛后才进入评分。评分的作用是安排审核优先级，不直接替代编辑。

### 6.1 基础维度（0–5）

| 维度 | 判断问题 |
|---|---|
| 独特性 `U` | 东京其他地方或其他时间是否很难获得同类体验？ |
| 质量证据 `Q` | 内容、制作、空间或主办者是否有可验证的高完成度？ |
| 体验密度 `X` | 到场后能看、摸、试、听或参与多少具体内容？ |
| 朋友价值 `F` | 是否容易产生共同话题、记忆或后续计划？ |
| 现在性 `N` | 是否新开、将结束、将消失或仅在特定周期出现？ |
| 可达性 `A` | 普通人是否容易理解规则、入场并完成体验？ |
| 信号可信度 `T` | 来源、日期和状态是否已经可靠核实？ |
| 商业空洞度 `C` | 是否主要是获客、广告、销售或行业寒暄？分数越高越差 |

建议初筛分：

```text
candidate_score = 2*max(U,Q) + X + F + N + 0.5*A + 0.5*T - 2*C
```

但正式发布仍需满足：

- `U ≥ 4` 或 `Q ≥ 4`；
- 至少一个具体、可引用的“为什么值得去”证据；
- 信息与入场资格已核实；
- 编辑愿意把它发给自己的某位朋友。

### 6.2 解释而非总分

用户不看总分，而看到：

- **为什么现在：** “三个月限定”“一般公开只有两天”；
- **具体看点：** “能现场操作陪伴机器人，不只是看展板”；
- **适合谁：** “适合喜欢机械、动物或奇怪产品的朋友”；
- **可能劝退：** “工作日、需预登记、部分展区偏行业”；
- **最佳去法：** “下午两点后人少，预计停留两小时”。

## 7. 探索队列生成

### 7.1 有限队列

参考 Steam 的有限探索逻辑，每轮 12–20 项，不做无限流。群组队列建议配比：

| 比例 | 内容 |
|---|---|
| 30% | 与成员明确兴趣相符 |
| 20% | 朋友中至少一人的强兴趣，其他人未明确拒绝 |
| 20% | 新开、将结束或即将消失 |
| 15% | 编辑精选的跨兴趣惊喜项 |
| 10% | 朋友或相似群组真实想去过的内容 |
| 5% | 完全新领域的受控探索 |

队列必须保证类型和场景多样性，避免连续出现十个展览或十家咖啡店。

### 7.2 过滤顺序

```text
全局合格池
→ 日期与营业状态
→ 群组任何成员的硬限制
→ 距离、预算、语言与入场资格
→ 已看过／本轮忽略
→ 群组兴趣聚合
→ 新颖性与多样性重排
→ 12–20 项队列
```

### 7.3 三态判断

- 右滑／想去：强正反馈；
- 上滑／可以：弱正反馈；
- 左滑／不想去：本轮负反馈。

投票在所有人完成前默认隐藏，减少从众。匹配结果分为：

- **全员想去：** 所有人强正反馈；
- **强匹配：** 多数想去，其余至少可以；
- **惊喜匹配：** 与历史偏好距离较远但无人反对；
- **暂不成立：** 有明确拒绝或现实限制冲突。

群体排序不取简单平均。先执行“最少痛苦”排除明显反对项，再优先选择至少一人高度兴奋、其他人愿意接受的选项。

## 8. 两条社交路径的具体交互

### 8.1 朋友组 → 活动

1. 创建 2–6 人临时或长期小组；
2. 选择一个时间窗口：“今晚”“这个周末”“九月找一天”；
3. 每人填写硬限制，可选择不公开具体原因；
4. 系统生成同一候选集合，成员异步滑动；
5. 揭晓匹配，显示共同理由而非只有爱心动画；
6. 进入计划页：投票具体场次、预约负责人、集合点和后续安排；
7. 到访后只问三件事：值得专程去吗、描述真实吗、会推荐给哪类朋友。

### 8.2 活动 → 朋友

1. 用户在活动页点击“想去”；
2. 可见范围：仅自己、选定朋友、所有好友；
3. 系统显示“有 2 位朋友也想去”，但尊重双方可见设置；
4. 用户可以发送低压力询问：“我对这个有兴趣，你呢？”；
5. 对方只需回答想去／可以／不想去；
6. 一旦形成匹配，自动创建围绕该活动的临时组和日期投票；
7. 若原活动时间不合，系统以它为锚点生成 5 个相似替代项。

## 9. 兴趣图谱

数据模型应区分“喜欢内容”和“这次能否成行”：

```text
User --member_of--> Group
User --interested_in--> Item
User --follows--> Venue / Series / Curator
User --votes--> QueueItem
Group --receives--> Queue
Group --matches--> Item
Plan --anchors--> Item
Item --held_at--> Venue
Item --evidenced_by--> Source
```

负反馈原因必须分开：

- `taste_no`：确实不感兴趣；
- `constraint_no`：时间、价格、距离或资格不合；
- `seen_already`：已经去过；
- `bad_source`：信息可疑或描述不符。

否则系统会把“这周没空”误学成“永远不喜欢机器人”。

## 10. 编辑后台

编辑后台比前台滑动更早建设，至少包含：

- 候选收件箱与来源过滤；
- 自动排除原因及人工恢复；
- 重复事件合并；
- 官方来源与媒体来源并排核实；
- 入场资格检查；
- 质量／独特性评分与证据字段；
- 发布、定时复核、过期和取消；
- 来源异常告警；
- 用户反馈与“描述不符”处理。

关键运营漏斗：

```text
每周 1,000 条原始候选
→ 200 条通过硬排除
→ 60 条值得补充调查
→ 20 条编辑认可
→ 10–15 条进入主要探索池
```

不同用户看到的队列可以不同，但全局合格池必须保持高质量。

## 11. 实施顺序

### 阶段 1：信息雷达（最优先）

- 建立 50–100 个来源的注册表；
- 完成 Big Sight、主要博物馆、5 所大学和开闭店媒体适配器；
- 实现硬排除、实体去重和编辑候选箱；
- 连续四周人工发布每周 10–15 项。

### 阶段 2：个人探索队列

- 每日或每周生成 12 项；
- 想去、可以、不想去、关注；
- 记录负反馈原因；
- 用编辑精选解决冷启动。

### 阶段 3：朋友组探索

- 邀请链接、日期与硬限制；
- 隐藏投票、三态判断和匹配揭晓；
- 计划页与群聊分享。

### 阶段 4：活动找朋友

- 想去状态的朋友可见范围；
- 兴趣重合通知；
- 活动临时组与替代活动队列。

### 阶段 5：个性化与来源网络

- 关注场馆、系列和编辑；
- 相似小组行为信号；
- 校园侦察员和用户投稿信誉；
- 只在已有足够行为数据后引入复杂推荐模型。

## 12. 成功指标

不要以浏览时长或滑动次数为第一指标。核心指标应是：

- 队列完成率；
- 单项“想去”率；
- 发送给朋友率；
- 小组全员完成率；
- 每组产生共同兴趣的比例；
- 匹配后确定日期的比例；
- 实际到访确认率；
- 到访后“值得专程去”比例；
- 内容描述与现场一致率；
- 每周至少发现一个用户原本不知道、最终实际去过的项目。

## 13. 一句话架构

> **先用广泛信息雷达找到东京正在出现、发生和消失的候选；再用硬规则排除职业与商业噪声，以编辑判断保证“好或独特”；最后像 Steam 探索队列一样，把有限候选交给个人和朋友组逐个判断，并把共同兴趣直接推进成计划。**
