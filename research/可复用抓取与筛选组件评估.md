# 东京近期有趣活动：可复用抓取与筛选组件评估

调研日期：2026-08-27（Asia/Tokyo）

## 结论先行

第一阶段不应该开发“万能爬虫”，也不应该把大模型塞进网站请求链路。建议把数据采集做成独立的定时批处理：优先消费 RSS、Atom、JSON-LD、ICS 和站点地图；没有结构化数据时再用 HTML 选择器；只有必须执行 JavaScript 的来源才启动浏览器。

建议立即采用的基础栈：

| 能力 | 采用组件 | 决策 |
| --- | --- | --- |
| 静态 HTML 与 JSON-LD | [Cheerio](https://github.com/cheeriojs/cheerio) | 立即采用。MIT；轻量，适合为每个东京来源编写很薄的适配器。 |
| RSS / Atom / JSON Feed | [Feedsmith](https://github.com/macieklamberski/feedsmith) | 立即采用。MIT；直接理解 feed 语义，比自己处理 XML 标签更稳。 |
| sitemap 与非 feed XML | [fast-xml-parser](https://github.com/NaturalIntelligence/fast-xml-parser) | 立即采用。MIT；留给 sitemap 和少量自定义 XML。不要与 Feedsmith 重复处理 RSS。 |
| robots.txt | [robots-parser](https://github.com/samclarke/robots-parser) | 立即采用。MIT；支持 RFC 9309、Allow/Disallow、Sitemap 和 Crawl-delay。 |
| 日语日期 | [chrono-node](https://github.com/wanasit/chrono) | 立即试用。MIT；原生提供 `ja` locale，和现有 Node 管线一致。关键日期仍需来源级测试。 |
| ICS / 周期事件 | [ical.js](https://github.com/kewisch/ical.js) | 有来源提供 ICS 时采用。MPL-2.0；支持 RFC 5545 和 RRULE。注意东京时区定义。 |
| 动态网页与可靠队列 | [Crawlee](https://github.com/apify/crawlee) | 按需采用。Apache-2.0；只用于 JS 必需、分页复杂或容易失败的来源，避免所有页面都启动浏览器。 |
| 日语语义去重 | [Ruri v3 30m](https://huggingface.co/cl-nagoya/ruri-v3-30m) | 优先实验。Apache-2.0；36.7M 参数、256 维、日语专用，适合标题/简介近重复与主题相似度。 |
| 跨语言语义去重 | [multilingual-e5-small](https://huggingface.co/intfloat/multilingual-e5-small) | 作为对照实验。MIT；支持约 100 种语言、384 维，适合日英混合来源。 |

核心边界是：这些组件负责“把信息可靠地带回来并归一化”，我们只自行实现真正有产品价值的部分——东京来源目录、开放性判断、独特性信号、负面类别规则、编辑审核和朋友共同兴趣。

## 推荐架构

```text
来源注册表
  ├─ RSS / Atom / JSON Feed ── Feedsmith
  ├─ ICS ───────────────────── ical.js
  ├─ sitemap / XML ─────────── fast-xml-parser
  ├─ 静态 HTML / JSON-LD ───── Cheerio
  └─ 动态 HTML ─────────────── Crawlee + Playwright（按需）
                    │
                    ▼
           统一 EventCandidate schema
                    │
       robots、限速、缓存、内容哈希、来源追踪
                    │
                    ▼
   硬排除 → 日期/地点/公众开放性 → 去重 → 兴趣评分
                    │
                    ▼
             待审池 → 已发布活动池
                    │
                    ▼
          网站展示 / 小组滑动 / 共同兴趣
```

采集任务与前台网站应分开运行。模型权重和浏览器不应进入 Cloudflare/Vinext 的页面运行时；定时任务生成版本化 JSON 或写入数据库，前台只读取已经审核过的数据。这样模型或某个来源失效时，网站仍能显示上一版可靠结果。

## 组件逐项判断

### 1. Cheerio：代替正则解析 HTML

当前采集器若依赖正则切 HTML，遇到嵌套标签、属性顺序变化和 HTML entity 很容易静默丢数据。Cheerio 使用 parse5/htmlparser2，提供 CSS selector，足以覆盖 Big Sight、展馆、大学和商圈的大多数静态列表页。

每个来源只实现：

- `discover()`：找到候选详情页 URL；
- `extract()`：提取标题、日期、地点、图片、简介和购票链接；
- `sourcePolicy`：抓取间隔、允许路径、可信度与默认受众；
- 小型 fixture 测试：保存一份脱敏 HTML，防止站点改版后无声失败。

不要试图写一套跨所有网站的万能 selector。

### 2. Feedsmith + fast-xml-parser：结构化来源优先

Feedsmith原生支持 RSS、Atom、RDF 和 JSON Feed，并对真实世界里不完全规范的 feed 做容错。它适合大学新闻、画廊公告、街区媒体与店铺博客。

fast-xml-parser适合 sitemap 与场馆自定义 XML。两者职责分开，可避免自己维护 namespace、CDATA、数组/单元素差异。

### 3. chrono-node 与 ical.js：日期不能靠一个正则

东京活动常见表达包括日期区间、跨月、休馆日、每周某日、预约时段和“本周末”。chrono-node 已有日语 locale，可先处理页面文本中的自然语言日期；ical.js 用于已有 ICS 和周期规则。

但日期解析必须保留：

- 原始日期文本 `dateText`；
- 解析结果 `startsAt` / `endsAt`；
- `Asia/Tokyo` 时区；
- 解析置信度与警告；
- 展期和单次场次的区别。

低置信度日期只能进入待审池，不能自动发布。

### 4. Crawlee：升级路径，不是默认路径

Crawlee提供请求队列、重试、会话、存储，以及 CheerioCrawler / PlaywrightCrawler 等层级。它适合需要翻页、JS 渲染或交互的票务和展馆页面。

首批来源不宜全面迁移到它：浏览器任务慢、依赖重，也更容易触发站点防护。先用 `fetch + Cheerio`，来源适配器显式标记 `render: "browser"` 时才交给 Crawlee。

### 5. changedetection.io：作为监视器，而不是嵌入产品

[changedetection.io](https://github.com/dgtlmoon/changedetection.io) 是成熟的网页变化监控服务，Apache-2.0，支持可视选择器、浏览器步骤、变化 diff、Webhook 和 RSS 输出。它尤其适合：

- 没有 feed 的大学开放日页面；
- 小店“闭店通知”“即将结束”页面；
- 不值得每天完整抓取、但一变化就应重新抽取的页面。

建议后期以独立 sidecar 部署，通过 Webhook 唤醒我们的抽取任务；不建议复制其实现或把整个服务嵌入前台仓库。

### 6. Trafilatura / Extruct：Python 丰富化 sidecar 的候选

[Trafilatura](https://github.com/adbar/trafilatura)（Apache-2.0）适合从文章型页面抽正文与元数据；[Extruct](https://github.com/scrapinghub/extruct) 可一次提取 JSON-LD、Microdata、Open Graph、RDFa 等嵌入元数据。

它们很强，但会引入 Python 运行面。MVP 中先用 Cheerio 读取 JSON-LD/Open Graph；只有当来源扩到大量长文章、店铺报道且正文噪声成为主要问题时，再加入 Python 丰富化任务。

## Hugging Face 模型选择

### 推荐先做 A/B：Ruri v3 30m 对 multilingual-e5-small

Ruri v3 30m 是日语专用 Sentence Transformer，模型卡给出的规模为 36.7M 参数、256 维、最长 8192 tokens，Apache-2.0。我们的主数据是日语短标题和简介，它应作为首选实验模型。

multilingual-e5-small 为 12 层、384 维，支持约 100 种语言，MIT。它适合日语、英语、中文混杂的活动来源，也有成熟的 ONNX / Transformers.js 生态。

先不要凭模型榜单决定。建立约 200 对东京活动样本，人工标注：

- 同一活动的重复页面；
- 同系列但不同日期/场次；
- 标题相似但实际不同的活动；
- 日英双语页面；
- 连锁店不同分店与同店重复报道。

用 pairwise precision/recall 决定模型和阈值。语义模型只产生候选重复组，最终合并还必须比较日期、场馆、主办方和 canonical URL。

### 暂缓 BGE-M3

[BGE-M3](https://huggingface.co/BAAI/bge-m3) 支持多语言、8192 tokens、dense/sparse/ColBERT 多种检索方式，MIT，但 1024 维且明显更重。当前问题不是做大规模通用搜索，而是几千到几万条东京候选的去重和兴趣匹配；先用小模型更经济。

### 分类模型只做第二意见

[multilingual-MiniLMv2-L6-mnli-xnli](https://huggingface.co/MoritzLaurer/multilingual-MiniLMv2-L6-mnli-xnli) 是 MIT 的多语言 NLI/zero-shot 模型，可以试验“招聘/职业说明/纯 B2B/公众可参与/具有实体体验”等标签。但其训练语言说明并未清楚证明日语质量，不能直接上线。

正确顺序是：

1. 高精度硬排除词与来源规则先拦截招聘会、合同说明会、学校招生说明、纯采购/批发展；
2. 明确优质来源和编辑白名单直接提高可信度；
3. 分类模型只处理模糊项并给出标签概率；
4. 模糊或新类别进入人工待审，不自动丢弃。

这可防止模型把“机器人产业展”误判为普通 B2B 展而删除，也防止把带有“体验”字样的招聘活动放进活动池。

## 不建议采用或暂缓

| 组件/做法 | 原因 |
| --- | --- |
| Talisman | 功能适合模糊匹配，但上次代码提交停在 2021 年。基础标题归一化可自己写少量确定性代码，语义近重复交给 embedding。 |
| 所有页面默认 Playwright | 成本和故障面太大；会让新增来源变慢。 |
| 通用事件抽取大模型直接生成数据库记录 | 日期与票务信息不可静默幻觉；应优先结构化字段和可追溯原文。 |
| 纯关键词“有趣度” | 只能做硬排除和弱信号，不能识别氛围、稀缺性、朋友同行价值。 |
| 把模型放到用户页面请求中 | 延迟、成本和可用性都不必要；离线批处理即可。 |

## 我们仍需自行实现的最小部分

不是重复造基础库，而是实现薄的产品层：

1. `SourceDefinition`：来源 URL、格式、抓取频率、适配器、robots 策略、可信度；
2. `EventCandidate`：原文、规范字段、来源证据、解析警告；
3. hard-block 规则：招聘、职业说明、招生、纯销售，以及白名单例外；
4. exact/hash/semantic 三层去重；
5. “好或独特”评分证据：稀缺、可体验、环境氛围、公众开放、朋友同行、时间压力；
6. 编辑待审队列和发布状态；
7. 前台活动卡展示 `为什么值得去`、来源与最后核验时间。

## 两周内的接入顺序

### 第 1 批：让数据真实、稳定地增长

- 将现有正则 HTML 解析替换为 Cheerio；
- 建立来源注册表与统一 schema；
- 加入 robots-parser、缓存、限速、失败重试和每来源健康统计；
- 接入 Feedsmith、fast-xml-parser、chrono-node；
- 首批覆盖 Big Sight、主要展馆/美术馆、大学开放活动、街区文化媒体和可公开访问的店铺公告；
- 前台只显示仍在有效期内且通过审核的活动。

### 第 2 批：减少重复与发现漏网之鱼

- 建 200 对日语去重测试集；
- 本地批量评估 Ruri v3 30m 与 multilingual-e5-small；
- 对“快闭店、即将结束、刚开业”加入变化监视来源；
- 仅为确实依赖 JS 的页面接入 Crawlee；
- 增加待审页，显示原始证据与每个过滤/评分步骤。

## 验收指标

比“抓到了多少条”更重要的是：

- 未来 30 天内，每周至少有 30–50 条值得滑动的候选，而不是职业说明噪声；
- 硬排除类别进入发布池的比例低于 1%；
- 同一活动重复卡片低于 3%；
- 每条活动都有原始 URL、最后核验时间和日期原文；
- 来源失效 24 小时内可见告警，不会悄悄变成空列表；
- 新来源从注册到首批候选不超过半天；
- 人工审核能够解释“为什么收录/为什么过滤”。

## 最终建议

现在就采用 Cheerio、Feedsmith、fast-xml-parser、robots-parser 和 chrono-node，按来源需要补 ical.js；把 Crawlee、changedetection.io、Trafilatura/Extruct 放在明确触发条件之后。模型先做离线评测，优先比较 Ruri v3 30m 与 multilingual-e5-small，不让模型承担不可逆的删除或发布决定。

这条路线最大限度复用成熟部件，同时把工程时间集中到真正形成壁垒的地方：来源覆盖、东京语境中的独特性判断，以及让一群朋友找到共同想去的东西。
